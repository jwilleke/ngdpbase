# ImportManager

ImportManager is the ICE engine ([#1979](https://github.com/jwilleke/ngdpbase/issues/1979)): one core manager that brings data in through format-specific __shims__ and hands the results to __receivers__. The design and its decisions are [ice-planing.md](../planning/ice-planing.md); this page is the reference for what is built. It also still holds the admin folder import, the URL import and the private-store takeout import.

## The engine

```text
upload (zip or files) | URL (fetched by the engine, #2109)
  └─ unzip ─ noise filter ─ SHA-256 fingerprint ─ skip unchanged
       └─ shim ─(chain)─ shim ─▶ receiver's own door (as the user / the job)
            per-file status + fingerprints ─▶ the engine's ledger
```

- __Shims__ know one outside format (D2). Each declares its direction (`in`, `out`, `both`), what it accepts (extensions, media types, kinds from another shim, and a "can I read this?" check), what it produces, and the receivers it may hand to (D3, D7). `'*'` (`ANY_RECEIVER`) in `receivers` means any receiver that takes the kind it produces, for a generic format shim such as `core.csv` ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)); each receiver still decides with its own permission. Types: `src/ice/types.ts`.
- __Receivers__ are doors that already exist (D4). The engine hands each result to the receiver's `receive(item, ctx, info)` and never writes content itself. The receiver checks its own existing permission with `ctx` (D5): there is no import permission. The engine asks the receiver's `mayUse(ctx)` first, before any work of a run ([#2012](https://github.com/jwilleke/ngdpbase/issues/2012)): on a no (or a throw) every uploaded file is `refused` ("You may not import into …"), and nothing is unpacked, read by a shim, kept or fetched. Each refused file is recorded in the ledger by its fingerprint, keeping its references and a kept original's reference, and never over a file the scope already took. `keepOriginalsAtUpload` keeps nothing for such a user. `receive` still checks each item.
- __Chaining__ (D9): a shim's output goes to the next shim that accepts its kind, until the item is a kind the receiver takes, from a shim that lists that receiver. DOCX → HTML → NCM → pages is one.
- __Duplicates__: a shim says which kind applies. `file` (the default): a file whose fingerprint its scope already imported is `unchanged` and skipped. `item`: the file is read again and each item whose `itemKey` the scope has seen is skipped. A file's item keys are read from the ledger once and written once (`seenItems`, `recordItems`), not per item, since a feed holds thousands ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)).
- __A URL source__ ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109), D10): `{ type: 'url', url, name?, headers?, timeoutMs?, metadata? }`. After the receiver's `mayUse` says yes (on a no nothing is fetched), the engine fetches the URL as the run's one file through its one way out (`guardedFetch` with the site's egress policy, read per fetch, and default User-Agent), with the source's headers and timeout and at most `fetch-max-bytes`. A refused, failed or non-2xx fetch is the file's `failed` status, with the reason. The file carries the source's `metadata`, plus `sourceUrl`, and so does every item read from it. The source's headers and timeout also apply to every follow-up fetch a shim asks of the engine in that run (`tools.fetch`, the xml-index shim's item documents). The feeds add-on is the first user: its scheduled job runs `runImport` with a URL source per due feed.
- __Run options__ ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)): a request's `options` reach every shim of the run as `tools.options`, over the site's `ngdpbase.import.shims.<id>.options`: a feed source's parse settings (CSV delimiter, items path, id field, field map). Server-built only, never a value a client sent.
- __A receiver that settles each file__ ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)): a receiver may have `fileDone(ctx, info)`, called once per file whose shims read it through, after each item was handed to `receive` or skipped as already seen, with every item the file held (`info.items`) and the source's `metadata`. A receiver that holds a snapshot of a source (FeedManager: a feed's records) stores the whole source there and drops what it no longer holds; the items skipped as seen are still in the source. Its return is a note for the file's status; a throw fails the file, and its new item keys are not recorded, so the next run hands them again.
- __A receiver fed only by its owner__ ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)): `uploads: false` keeps a receiver off the import screen (`receiversFor`) and makes `enqueueUpload` refuse it. `feeds.items` is one: what a feed holds comes only from its source.
- __What counts as done__ ([#2010](https://github.com/jwilleke/ngdpbase/issues/2010)): `imported`, `duplicate` (every item already held) and `unchanged`. A file whose last status was `partial`, `failed`, `refused` or `unreadable` is read again on the next run, so items a receiver refused (a permission since granted, a record it now accepts) are offered again. Items of such a file that were stored are not handed over twice: while a `file`-duplicates file is not done, the ledger records an engine key for each item stored (`itemKeyOf`: the fingerprint, the chain and a hash of the item's content, plus a count for identical items; never its position), and a retry skips them. A retry whose items are all already stored, with nothing refused, is `unchanged` ("already imported") and done, even with a shim's partial note. A `partial` file whose stored items are now skipped and whose refusals remain stays `partial`, not `refused`.
- __The original__ (D11): the run's `original` is `cite` (each item carries a citation the receiver renders; pages get a footnote), `keep` (the receiver's own `keepOriginal`, else the `core.files` upload door, both as the user; refused means nothing is imported), or `none`. An original is kept once per fingerprint, scope and keeping door: the ledger records its reference as soon as it is kept, and a later run of the same bytes (a retry after a failed conversion or a refusal, or a per-item shim reading the file again) reuses it instead of keeping another copy.
- __Keeping into an encrypted store__ ([#2034](https://github.com/jwilleke/ngdpbase/issues/2034)): a receiver whose `keepOriginal` writes into an encrypted store (phr's vault) says so with `keepsEncrypted: true`. A background run carries a job context, which never holds the user's key, so such a keep cannot happen in the run. Instead `enqueueUpload(request, ctx)` keeps each original during the upload with `ctx`, the request's own context, while the key is in it, then queues the run with the job context derived from it: the bytes and the store's sealed index entry are written then. Each one is recorded in the ledger as the keep-once record, so the run reuses it and never keeps again; signing out right after the upload changes nothing. The files are chosen exactly as the run chooses them (`keepOriginalsAtUpload` and the run share `planFile`): zip members each, never noise, a file too large, one nothing reads or one already imported. A keep refused (or failing) at upload throws `ImportUploadRefused`, naming the file, and nothing is queued; originals kept before it stay recorded for the next try. Keeps through `core.files`, or a receiver without `keepsEncrypted`, still happen in the run.
- __Media types__ ([#2061](https://github.com/jwilleke/ngdpbase/issues/2061)): every file the engine unpacks from a zip carries a `mediaType`, from its extension (`MEDIA_TYPE_BY_EXTENSION` in `src/ice/fileHandling.ts`, the one table, which the folder import uses too), checked against its bytes: JSON must start with `{` or `[`, NDJSON with `{`, XML with `<`, else it is `application/octet-stream`; then the upload door's own rule (`resolveUploadMime`), so bytes that show a type decide (XML with an `<?xml` prolog is `text/xml`) and the type a receiver is handed is the type the door stores. A file uploaded on its own keeps the type its request gave it. The table is code, not configuration: it says what a format is; which types a site takes is its attachment allow-list.
- __The types a receiver keeps__ ([#2061](https://github.com/jwilleke/ngdpbase/issues/2061)): a receiver may declare `originals.types`, exact media types (a wildcard is refused at registration). For each keep at upload the engine opens an `OriginalKeep` (`src/ice/originalKeep.ts`) for that receiver, that user and that one `keepOriginal` call, hands it to the call, and closes it when the call returns. The receiver passes it to `uploadAttachment` as the `keep` option. The door honours only an open one, and only for a file going into that user's own vault of a system-category the receiver's add-on declares (`StoreKind.owner`): there the declared types are allowed beyond `ngdpbase.attachment.allowedtypes`, and the file is marked a download. Anywhere else (the shared pool, another vault, an ordinary upload, another receiver, a copy of the object, after the call) it changes nothing, and undeclared types and size limits are as always. Keeps in the run (`core.files`, a receiver without `keepsEncrypted`) get no `OriginalKeep`.
- __The original choices a receiver offers__ ([#2021](https://github.com/jwilleke/ngdpbase/issues/2021)): a receiver may declare `originals: { allowed, default }`. Without it all three are offered. A run that chooses nothing gets the receiver's default (else `default-original` when allowed, else the first allowed); a run asking for one the receiver does not offer is refused.
- __The name a user gives__ ([#2130](https://github.com/jwilleke/ngdpbase/issues/2130)): a receiver that applies a name declares `names: 'title'` (a page's title) or `names: 'file'` (a file's name). An upload file's `givenName` (`IceUpload`) reaches such a receiver as `ReceiveInfo.givenName`, after the engine checks it with the one rule in `src/ice/givenName.ts` (`givenNameProblem`): not empty, at most `name-max-length` characters, no control characters; for a title, the page title rule (`pageTitleRule`); for a file, no `/` or `\`, no leading dot, and the upload's own extension. A name that breaks the rule makes the file `refused` with why; a name equal to the default (`defaultGivenName`: the file's own name, for a title without its extension) is not passed, so the receiver names it as it always has. A zip's files never carry one (the engine drops it when it unpacks), and a receiver without `names` is never handed one: it names what it creates itself. The name is a name only: the receiver's door decides where the thing goes, as without one. The receiver refuses an item whose given name its location already has, never replacing it ([#1855](https://github.com/jwilleke/ngdpbase/issues/1855): a taken name warns before replacing; a background run cannot ask, so it refuses and the user imports again with another name). A refused file is not done, so that retry is read again. The report and the ledger keep the given name beside the file's own (`givenName`) only when something was stored under it.

  A name given is never silently dropped (operator, 2026-10-29). When the file is already on the site under another name, its status says so, "This file is already on the site as "scan0042.pdf"; rename it there." (`alreadyHereAs`), with `link` to it when the receiver's `linkFor` says the user may open it (a path on this site only, `receiverLink`), and the given name is not recorded. Two ways this happens. First, the receiver holds the same content under another name: it answers `duplicate` with `heldAs` (`core.files`, whose pool stores by content). The file is then `duplicate`, a done status, as for any held item, and the ledger keeps `heldAs`. Second, the scope already took the same bytes (by fingerprint): the file is `unchanged`, as before, and the message names what it became (`heldAs`, else the name it was given, else a page's title, else the file's own name). `duplicate` and `unchanged` rather than `refused`: nothing is wrong with the file, and reading it again changes nothing, so a retry with yet another name gets the same answer; the fix is a rename where the thing is. The same bytes under the name they already have get today's "already imported", and without a given name nothing changes.
- __Off the request path__: `enqueueImport` (or `enqueueUpload`, for a user's upload) queues the run for the background job `import.engine-run` and returns its id at once. `runImport` runs and waits, for code already off the request path.

| --- | --- |

| `core.docx` | Produces `html`, which chains into `core.html` |
| `core.pages` | PageManager's save door. Checks `page-create`. A title that exists is a duplicate. Fix steps and the NCM footnote step run as for the folder import. `names: 'title'`: a given name is the page's title, over any the file gives; a given title a page has is refused. Its `page-create` audit record carries `importedFrom` (the file's own name) beside the title |
| `core.csv`, `core.geojson`, `core.rest-json`, `core.xml`, `core.rss-atom`, `core.xml-index` | The record shims ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109), `src/ice/shims/`; moved into core from the feeds add-on by the operator's decision of 2026-10-29, generic work goes to core). Each reads one structured format into `record` items, per-item duplicates (the key is the record's id with a hash of its content), and hands to any receiver that takes records (`receivers: ['*']`). Their settings are generic options, from the site (`ngdpbase.import.shims.core.<name>.options`) or the run (`options`): `itemsPath`, `recordIdField`, `map`, `delimiter` and `skipLines` (CSV), `linkPattern` and `maxItems` (XML index, which asks the engine to fetch each linked document). Detected by extension (`.csv`/`.tsv`, `.geojson`, `.json`, `.xml`, `.rss`/`.atom`) or named by the run; `core.xml-index` only when named. The feeds add-on names one per source; accounting's bank statements ([#2121](https://github.com/jwilleke/ngdpbase/issues/2121)) can use `core.csv` with no add-on enabled. XML parsing is `fast-xml-parser`, now a core dependency |
| `core.files` | AttachmentManager's upload door, which checks `asset-upload`. Also keeps originals for receivers that do not keep their own. Offers only `none` for the original: the file stored is the original. `names: 'file'`: a given name is the stored file's name (its media type is still the upload's); a given name the shared pool has is refused (`getSharedPoolAttachmentByFilename`). Its `asset-upload` audit record carries `importedFrom` beside `filename`; when the pool already held the bytes it records `stored: false`, the name they are held under (`filename`, `heldAs`) and the name offered (`offeredAs`), never the given name as if stored ([AttachmentManager](AttachmentManager.md)). A kept original keeps its own name |
| `core.ncm-html`, `core.ncm-file`, `core.html-file`, `core.markdown-file`, `core.pdf` | Core's `out` shims, for export ([#2120](https://github.com/jwilleke/ngdpbase/issues/2120), `src/ice/shims/export.ts`). `ncm-html` renders NCM into an HTML document (ExportManager's page document) and is offered only as a step. The others make the file: the page's NCM as stored (`.md`), the HTML document (`.html`), the rendered page as plain Markdown (turndown, `.md`), and a PDF through `ExportManager.htmlToPdf` ([#1974](https://github.com/jwilleke/ngdpbase/issues/1974)), offered only while `ngdpbase.export.pdf.provider` is not `none`. Reading a PDF in (D3's other half) is not built, so `core.pdf` is `out` only. Before the HTML goes to the provider, `withoutRemoteUrls` takes out every URL that is not `data:` (attributes, `style`, `<style>`, and the elements that load by being there), so a remote provider is never made to fetch from its network; links (`<a href>`) stay |

Core's kinds are `file`, `html`, `ncm` and `record`: one structured row or entry, whose `data` is `{ id, properties }` (`IceRecordData`), so a format shim serves any receiver that takes records ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)).

Every registered converter is also a shim, `core.<formatId>`; `registerConverter` still works.

Each with its result, message, time, receiver, how many references, and a `link` when the receiver's `linkFor` says the user may open the first. Throws `IdentityStoreUnavailableError` when whose entries they are cannot be told |
| `givenNameProblem(receiverId, given, original)` | Why a name the user gave cannot be used for this receiver, or null ([#2130](https://github.com/jwilleke/ngdpbase/issues/2130)): the engine's rule with the site's `name-max-length`; a receiver without `names` takes none. For `POST /import`, to answer at once; the run checks again |

| `exportFormatsFor(sourceId, ref, ctx)` | The formats the Export action offers this user for one thing: none when the source's `mayExport` says no, else each enabled `out` shim that makes a `file` and is reachable from what the source yields, with its chain |
| `startExport({ source, ref, format }, ctx)` | With the request's context: the source reads the thing now, then the chain runs in the ICE job as `jobContextFromRequest(ctx)`; returns the run id. A request is `{ source, receiver, shim?, original?, scope?, options? }`, where `source` is `{ type: 'upload', files }` (each `{ name, bytes, mediaType?, givenName? }`) or a URL source. Each file's report has its status: `imported`, `partial` (a shim's partial note, or some items refused), `unchanged`, `duplicate`, `noise`, `unreadable` (no shim reads it for that receiver), `refused` (the receiver's permission said no, before any work, or for every item), or `failed`. A file's `message` carries what the receiver said of what it stored (`ReceiveOutcome.message`, such as "12 new, 0 updated, 0 unchanged"), before any partial note and refusal; when several items say different things it shows the first and how many more, so the per-file status at /import stays short.

### Where fingerprints and status live

The engine's own ledger (`src/ice/ledger.ts`), behind the `IceLedger` interface: one JSON file per scope under `ngdpbase.import.engine.ledger-dir`, holding each file's name (and the name the user gave it, `givenName`, #2130), fingerprint, size, status, message, time, the receiver's references and the kept original's reference with the door that kept it, and the item keys seen. Never the content. A scope is bound to the receiver and the user the run is for ([#2013](https://github.com/jwilleke/ngdpbase/issues/2013)): `boundScope(receiver, owner, sub?)`, `ice2/<receiver>/<owner>[/<sub>]` with each part URI-encoded, where `owner` is the user's identity `@id` (`IdentityManager.identityIdOf`, with a system context stating the reason), else their username ([#2041](https://github.com/jwilleke/ngdpbase/issues/2041)). ImportManager works it out from the run's context; a request's `scope` only narrows within that user's own (phr's source id), so one user's entries never skip, mark duplicate or show another's files, and a later account reusing a username has another `@id` and inherits nothing. Each ledger file carries `form: 2` and its scope: a file written before the binding is read as empty (it belongs to nobody), so files imported before it are imported once more, and receivers' own duplicate checks (a page title, per-item keys) catch what they already hold. The old files stay on disk untouched. The username is used only when the identity store answers that the user has no identity record: ImportManager asks `canAnswer()`, then `getByUserIdentifier` (which throws when the store cannot answer, unlike `identityIdOf`). When the store cannot answer, `runImport`, `enqueueImport` and `enqueueUpload` throw `IdentityStoreUnavailableError` before anything is kept, queued or recorded; `POST /import` answers 503, "Imports cannot start right now. Try again shortly." The application database is off by default, so this is the first store; a table implements the same interface when it is on.

## The import screen (/import)

Any user's screen onto the engine ([#2021](https://github.com/jwilleke/ngdpbase/issues/2021)), in `WikiRoutes` (`importPage`, `importUpload`, `importRunStatus`) and `views/import.ejs`. Gated by `profile-manage`, which every user holds, so an anonymous visitor is sent to sign in; there is no import permission (D5).

- `GET /import` offers the receivers `receiversFor` gives this user, their runs still queued or running from `importRunsFor`, and "Your recent imports" from `recentImportsFor`, so the list survives a restart. A file given a name shows that name, with the file's own beside it, there and on the live status ([#2130](https://github.com/jwilleke/ngdpbase/issues/2130)). Each receiver comes with its `names`, so the screen offers a name field for one chosen file (not a zip) into a receiver that takes a name, pre-filled with the default (`defaultGivenName`); the field is disabled, and not posted, otherwise. When the identity store cannot answer, the list says it cannot be shown right now. `?receiver=<id>` preselects one, only when it is among them. With none, the screen says there is nothing they can import into.
- `POST /import` (multipart: `files`, `receiver`, `original`, `name`; sent with `csrfFetch`) checks the receiver is one of theirs and the original choice one it offers, and a `name` against `givenNameProblem` (400 with why; a 400 too for a name with a zip or several files, or for a receiver without `names`), then calls `enqueueUpload` with the request's own context, which keeps originals into an encrypted store (#2034) and queues the run with `jobContextFromRequest`. The request is built from those fields only, never a client's `scope` or `shim`. It answers 202 with the run id at once. Over `upload-max-files` or `upload-max-bytes` is a 413, refused before anything is queued. An original that could not be kept in an encrypted store is a 403 whose `error` says which file and why; nothing is queued.
- `GET /import/runs/:runId` returns the run's report to the user it ran as; anyone else gets 404.

### File names of a confidential import ([#2110](https://github.com/jwilleke/ngdpbase/issues/2110))

The uploader sees every file name on their own status and recent list, and the audit log keeps what the receivers' doors record. When the destination is encrypted (`isConfidential`: a receiver with `keepsEncrypted`), file names are never written to application logs, notices or admin screens: the engine's failed-run log and `POST /import`'s failed-queue log give the run and the error's class (`errorClassOf`), never the message, which may name a file. A sealed store's upload door logs by id ([#1461](https://github.com/jwilleke/ngdpbase/issues/1461)). Every other import logs file names as before. `ImportManager.confidentialNames.test.ts` is the guard: it drives one distinctive name through every way a confidential run can end and fails if a log line or notice holds it, with a control run proving the search finds a logged name. A test, not a static check: a file name reaches a log through a variable or an error's message, which no pattern over the source can see.

The end-user help page is [Importing Files](../../required-pages/979ca807-b5fd-4993-a101-d619fe9b6362.md).

## Export ([#2120](https://github.com/jwilleke/ngdpbase/issues/2120))

Export starts from the thing being exported (operator, 2026-10-28): there is no general export screen. The thing's owner registers an __export source__ (`IceExportSource`, `src/ice/types.ts`): what kind of items it yields, `mayExport(ref, ctx)` (an affordance, recording nothing) and `read(ref, ctx, info)` (the door, checking the owner's existing permission and recording the export). The engine (`src/ice/runExport.ts`) offers the `out` shims that make a `file` and can be reached from that kind, each by its shortest chain (`exportChains`), and runs the chosen one (`runExportChain`), with `max-bytes` on the source and on every step, ending with exactly one file.

- __Pages__ (`core.pages`, yields `ncm`). Offered when the reader may see the page (`mayShowPage`) and holds `page-export`. Read by asking `page-export` (for a vault page, in the vault, as `hasPermissionOn` asks it, [#1539](https://github.com/jwilleke/ngdpbase/issues/1539)), then the page door (`readPage`), which decides `page-read` and records a refusal. A user who holds `page-export` there but whose sign-in is not fresh enough for it is given the step-up prompt, not a 404. Each export is recorded as `page-export` with the page, the format and the run id once the run has ended (the source's `recordExport`): `success` only when the file was made, else `failure` with the reason the user was shown, also when what was read is not exported (over `max-bytes`, the site too busy) (D5: no new permission). The single-page `/export/html` and `/export/markdown` routes are unchanged, gated on read only ([#1060](https://github.com/jwilleke/ngdpbase/issues/1060)).
- __Off the request path.__ The source reads in the request, with everything the request carries (step-up, a vault's key); the shims run in the ICE background job, `import.engine-run`, which drains imports and exports alike, each as the job context of the user who asked. `tools.ctx` hands that context to an `out` shim (`ExportShimTools`).
- __The file__ is held in memory, never on disk, so an export of a sealed vault's page never rests unencrypted. It is the asking user's alone and is let go after `keep-minutes`, or sooner to make room under `max-held-bytes` and `max-kept-runs` (finished runs only, the user's own first). A failed run says why in plain words; its log line gives the run, the format and the error's class, never the message.

The Export action on a page, in `WikiRoutes` (`exportPageFormats`, `exportPageStart`, `exportRunStatus`, `exportRunDownload`) and `views/export-item.ejs`, asks `page-export` at every route's door (`permitted`), and no other permission (D5); a stale sign-in is sent to step-up there. A page's More menu links to it for a signed-in user who holds `page-export`, so the link is shown to exactly those the routes let in. The engine also refuses anyone not signed in (`signedIn`), whatever a site grants anonymous, since a run is held for its user.

- `GET /export/page/:page` lists `exportFormatsFor('core.pages', page)`; none is a 404, whatever the reason.
- `POST /export/page/:page` (`{ format }`, sent with `csrfFetch`) answers 202 with the run id; a page they may not export, or a format not offered, is a 404; one that needs a fresh sign-in is the step-up answer (`reauth`, which the page follows); over `max-bytes` a 413. More than 20 starts a minute by one user (`exportStartRateLimiter`), `max-queued-per-user`, or a site with no room left is a 429. The page stops waiting after about ten minutes and says the export is taking longer than expected.
- `GET /export/runs/:runId` is the run's status, and `GET /export/runs/:runId/download` its file, as an attachment with `nosniff` and `no-store`; anyone else, or a file let go, gets a 404.

## The folder import (/admin/import)

Unchanged for the user using it: preview, import (streamed), conflict policy, attachments from `-att/` folders, keyword registration, run summaries. Its conversion step now runs the converter's shim (and the DOCX → HTML chain) through the same code the engine runs. Gated by `admin-system`, as before.

## Known gaps

- [#2061](https://github.com/jwilleke/ngdpbase/issues/2061): only a keep at upload (`keepsEncrypted`) carries an `OriginalKeep`; a receiver that keeps in the run into an unencrypted vault of its own still meets the site's allow-list. An original kept through `core.files` is an ordinary attachment, shown inline (sandboxed) like any other.

- [#2120](https://github.com/jwilleke/ngdpbase/issues/2120): export is built for a page; search results and add-on lists have no export source yet, and `registerExportSource` is not on `host`, so an add-on cannot offer its own lists. A sealed vault's page is read with the request's key, so it exports, but an export source for a list of many things will need the same read-in-the-request care. Made files live in memory and are gone after a restart. The general `/export` screen and the mobile menu's Export link are still there.
- [#1979](https://github.com/jwilleke/ngdpbase/issues/1979): the takeout import and the admin URL import (`importFromUrl`) are not on the engine yet. Feeds are ([#2109](https://github.com/jwilleke/ngdpbase/issues/2109)).
- [#2109](https://github.com/jwilleke/ngdpbase/issues/2109): a URL source has no schedule of its own: its owner's background job decides when to run it (the feeds add-on's `feeds.poll`). A run with a URL source is a scope's file per fetch, so the ledger keeps one entry per distinct response body (capped at `ledger-max-entries`) and, for a per-item shim, one key per item version seen.
- [#2110](https://github.com/jwilleke/ngdpbase/issues/2110): "Your recent imports" lists what the ledger records, so a file skipped as noise or as unchanged, one too large, and an archive that could not be unpacked are shown only on the live run's status. Entries under a caller's narrower scope (an add-on's own source id passed as `scope`) are not listed. `core.files` has no `linkFor` yet (whether a user may read an attachment is decided in the attachment route, not in a manager), so a stored file is not linked. An original kept at upload shows as failed, "not imported yet", until its run records the result.
- [#2110](https://github.com/jwilleke/ngdpbase/issues/2110): only the engine and `/import` are guarded for confidential file names. A confidential receiver's own code (an add-on's `receive` and `keepOriginal`) must not log them either; the guard does not reach add-on code outside this repository.
- `core.pages` does not register JSPWiki categories as keywords, as the folder import does: that writes the site's keyword catalogue, which `page-create` does not cover.
- Run reports live in memory (`max-kept-runs`); the ledger keeps per-file status across restarts.
- [#2010](https://github.com/jwilleke/ngdpbase/issues/2010): the engine's keys for a retried file's stored items hash the item's content, so a shim whose output for an item changes between runs (a new version, an option) makes it look new, and the keys a scope keeps are capped at `ledger-max-entries`; a receiver's own duplicate check is then what prevents a second copy. A `duplicate` file is done: a page deleted since is not imported again from the same bytes. The exception is a receiver that `rechecks` an item itself: `core.private-store` hands a takeout's page with a uuid to its own uuid check every time, so a page deleted since an earlier import comes back ([#2118](https://github.com/jwilleke/ngdpbase/issues/2118), operator 2026-10-30).
- [#2013](https://github.com/jwilleke/ngdpbase/issues/2013): ledger files from before the binding are left on disk, unread, and every file is imported once more. `core.pages` finds a duplicate by the exact title it would save (`getPageMetadata(title)`); a title the save stores under a normalised name is not caught, so that one re-import can make a second page.
- [#2130](https://github.com/jwilleke/ngdpbase/issues/2130): a given name is checked when the run reaches the receiver, not reserved at upload, so two imports giving the same name close together: the second is refused. A file already on the site under another name is not renamed by importing it again: the status says where it is, and the user renames it there. `core.files` has no `linkFor`, so that status has no link for a file; pages are linked. Only `core.pages` and `core.files` apply a name; an add-on receiver opts in with `names`, and when its destination is encrypted it must keep `info.givenName` out of its logs as it keeps `item.name`.
- One background job run drains every queued import; its audit record names the first user in the queue. Each import still runs as its own user.
