# AddonsManager

Core add-on management system. Discovers add-ons in the configured `addons/` directories, registers them with the engine, manages their initialization lifecycle, and resolves dependencies between them. Enables optional business modules (journal, calendar, person-contacts, elasticsearch, etc.) to layer onto ngdpbase core without modifying it.

## Responsibilities

- __Discovery__ — scan `addons/*/package.json` for ngdpbase-add-on metadata.
- __Registration__ — call each add-on's `register(engine, config, host)` hook in dependency order: `dependencies` must be installed and enabled and load first; `optionalDependencies` load first when installed and enabled and are skipped otherwise (#1808).
- __Host__ — `host` is built per add-on by `buildAddonHost` (`src/utils/addonHost.ts`) and frozen: core's `ApiContext`, `ApiError`, `sendApiError`, `actorOf`, `jobContextFromRequest`, `jobContextFromSystem`, `guardedFetch`, `setEnabledForPerson` bound to the slug (#1963), a `logger` child tagged with the slug, and `recordAuditEvent` / `addonAuditEventName` limited to the events that add-on declares in its own `config/default-config.json` (read through `ConfigurationManager.getAddonDeclaredDefaults`). An add-on whose `register` takes two arguments still loads ([#1813](https://github.com/jwilleke/ngdpbase/issues/1813)).
- __Lifecycle__ — invoke `init` → `register` → `shutdown` in the correct sequence; per-add-on try/catch keeps a failing add-on from blocking the others.
- __Capability flags__ — addons can call `engine.setCapability(name, true)` to advertise their availability; consumers gate behaviour on `engine.hasCapability(name)`.
- __Profile-section hooks__ — addons that contribute to `/profile` register a `profileSection(user)` callback; AddonsManager fans the call out. The paired save hook is `saveProfileSection(ctx, body)` — since [#1234](https://github.com/jwilleke/ngdpbase/issues/1234) its first argument is the caller's context (`PermissionSubject`), forwarded to whatever the addon writes, never a username; an addon still on the old `(username, body)` shape is named in a warning at load and its saves fail per call.
- __Per-user add-ons ([#1963](https://github.com/jwilleke/ngdpbase/issues/1963))__ — `enabledAddonsFor(ctx)` returns the loaded add-ons whose manifest says `perPerson: true` and whose switch, the user's preference `<slug>.enabled` (`personSwitchKey`), is `true`. It reads those keys and no other preference. The switch is written only through each add-on's `host.setEnabledForPerson(ctx, on)`, bound to its slug, which asks the PDP for `profile-manage`. See [the addons developer guide](../guides/addons-developer-guide.md#per-user-add-ons-and-their-switch). Turning a switch on while the add-on's registered documents are not accepted at their current version refuses with `ConsentRequiredError` ([#1603](https://github.com/jwilleke/ngdpbase/issues/1603), [ConsentManager](ConsentManager.md)); `saveProfileSections` returns those refusals (`consentRequired`) so the profile can say so. `isPerPerson(slug)` answers whether an add-on is per-user (`perPerson: true`), for ConsentManager.
- __Listings ([#1965](https://github.com/jwilleke/ngdpbase/issues/1965))__ — `listedAddons()` returns the enabled add-ons whose manifest does not say `listed: false`: description, `family`, the About page (`ngdpbase.addons.<slug>.about-page` first, then the manifest's `aboutPage`), whether it is per-user, version and load state. It calls no add-on's `status()`, so a page can render it; `ConfigAccessor type='addons'` and `type='my-addons'` do, and show version and load state to `admin-read` holders only.
- __Dashboard cards / stylesheets__ — addons register UI surfaces here.
- __Load failures ([#1883](https://github.com/jwilleke/ngdpbase/issues/1883))__ — every enabled add-on that does not load, whatever the reason (a refusal before import, an import that throws, no `register()`, `register()` throwing, an unresolvable load order, or never found), goes through `recordLoadFailure`: its status carries the reason, and admins get one `error` notification, "Critical: add-on `<slug>` did not load". The "Add-on declaration problem" notification no longer repeats a refusal of an enabled add-on. When `ConfigurationManager.isAddonSiteCritical(slug)` is true it also calls `engine.maintenance.enter(reason)`, the one maintenance door ([#1906](https://github.com/jwilleke/ngdpbase/issues/1906)); the gate reads it per request, so the site starts in maintenance mode with `/admin`, `/login` and `/logout` open and visitors shown only the site's maintenance message (`ngdpbase.features.maintenance.message`). `app.ts` logs the add-on's reasons after `initializeAddons()`. The rule and the value's rules are in [the addons developer guide](../guides/addons-developer-guide.md#when-an-addon-does-not-load-site-critical).
- __Installing add-ons ([#1830](https://github.com/jwilleke/ngdpbase/issues/1830))__ — before discovery, installs or verifies the add-ons `ngdpbase.addons.install` names, into `<instance data folder>/addons/<slug>/`, and loads from there only the ones it verified. See below.

## Installed add-ons

AddonsManager owns the installer, because which add-ons a site has is add-on state and has one owner. The mechanics are utilities with no state of their own:

- `src/utils/addonInstaller.ts` — registry, integrity, the install and verify flow;
- `src/utils/addonProvenance.ts` — the Sigstore provenance check (`@sigstore/verify`, `@sigstore/bundle`);
- `src/utils/sigstoreTrustedRoot.ts` — the Sigstore trusted root from its TUF repository (`tuf-js`, seeded from `@sigstore/tuf`), downloaded through `guardedFetch` rather than tuf-js's own global `fetch`;
- `src/utils/addonTarball.ts` — reading and unpacking the tarball safely (`tar`);
- `src/utils/addonLock.ts` — the lock file, read synchronously by the configuration merge too.

Every outbound request (packument, tarball, attestations, TUF metadata) uses `guardedFetch` with the egress policy.

- __Config:__ `ngdpbase.addons.install` — a map of slug → `{ "package", "version", "repository" }`, default `{}`. Declared `sensitive` in `ngdpbase.config.sensitive-values`, because it says which software at which versions the site runs. An empty map does nothing: no folder, no request.
- __Tuning__ (all under `ngdpbase.managers.addons-manager.install.`): `registry` (default `https://registry.npmjs.org`, `sensitive`), `sigstore-tuf-url` (default `https://tuf-repo-cdn.sigstore.dev`, `sensitive`), `timeout-ms` (30000), `check-timeout-ms` (10000; bounds the newer-release check the admin page waits on, [#2100](https://github.com/jwilleke/ngdpbase/issues/2100)), `max-metadata-bytes` (16 MiB), `max-tarball-bytes` (50 MiB), `max-unpacked-bytes` (200 MiB).
- __Lock file:__ `<data>/addons/addons-lock.json`, `{ lockfileVersion: 1, addons: { <slug>: { package, version, integrity, installedAt, provenance: { repository, verifiedAt }, pending?, previous? } } }`. `pending` and `previous` have the same `{ version, integrity, installedAt, provenance }` shape: `pending` is a release an Update staged, `previous` the release a start switched away from, until the new one is confirmed loaded. The verified tarballs are in `<data>/addons/.packages/`, the TUF cache in `<data>/addons/.sigstore/`.
- __What loads:__ AddonsManager registers from `<data>/addons` only the slugs the installer verified on this start, even when `addons-path` names the folder; any other folder there is reported to admins and not loaded. The configuration merge takes an installed add-on's `config/default-config.json` layer only when the lock file and the install map both name it.
- __Boot order:__ `ConfigurationManager` counts a slug named in the install map as known, so an enabled add-on that is not installed yet does not refuse the boot (#672). An enabled id that only a stray folder in `<data>/addons` answers is logged and skipped by that check, never refused; an enabled id with no folder anywhere still refuses the boot as before. After an install, a repair or a rejection, AddonsManager calls `ConfigurationManager.reload()` so a new add-on's layer applies on this boot.
- __Audit:__ `addon-install` (on-failure `refuse`, written after every check and before anything is written) and `addon-verify-failed` (on-failure `continue`), through `recordSystemAction` under `systemContext`. `addon-update` (on-failure `refuse`): an administrator's Update, attributed with `actorOf(ctx)` and `{ package, fromVersion, toVersion, integrity, repository }`, written before the release is written; and a fall-back, under `systemContext` with `result: 'failure'` and `fallback: true` (that record's loss is logged, never undoes the fall-back).
- __Problems__ are logged and posted to admins through `NotificationManager` (`type: 'system'`), one per add-on: `<slug> not installed: <reason>`. The boot always continues.

### Update ([#2100](https://github.com/jwilleke/ngdpbase/issues/2100))

- `checkInstalledUpdates(ctx)` — asks the PDP for `admin-read` or `admin-system` (throws `AddonUpdateForbiddenError`), then, for each entry in the install map, the pinned and staged release, the range, the newest release in the range, the newest newer release this core can run (`available`) and the newest newer one that needs a newer core (`needsCore`). One packument request per add-on, through the guarded client, with `check-timeout-ms`. Registry unreachable is the answer `registryUnreachable: true`. Called by `GET /admin/addons`; never at start.
- `updateInstalledAddon(ctx, slug, version)` — asks the PDP for `config-manage` (throws `AddonUpdateForbiddenError`), then `stageUpdate`: the version must be a release in the range, newer than the pinned one, and need no newer core; it then passes the same `fetchVerified` door as a first install (sha512, provenance, contents, `package.json`). `addon-update` is recorded, then the tarball is written to `.packages/` and the lock entry gets `pending`. The running add-on's folder is not touched. Updates are serialized. While the lock still names `previous` (a switch not yet confirmed), an Update is refused with "finish the last update first: restart the site", and `checkInstalledUpdates` reports it as `blocked`: the next start's fall-back would drop anything staged then. Returns `{ status: 'staged' | 'refused', reason?, registryUnreachable?, failedCheck? }`; a refused check is also recorded as `addon-verify-failed`. Called by `POST /admin/addons/:name/update`, which asks `config-manage` (with step-up) first and carries the CSRF token.
- __No hot reload.__ An add-on cannot be unloaded: its modules stay in Node's module cache, and its routes, jobs and hooks stay registered. So an Update takes effect at the next start, and the page says "Restart the site to use version X".
- __The next start__ (`installConfiguredAddons`): a lock entry with `pending` that still answers the install map and whose tarball still matches its sha512 is switched to: the installed folder moves to `.previous-<slug>`, the new tarball is unpacked into `<slug>/`, and the entry becomes the new release with `previous` set. Otherwise the staged release is discarded with a notice and the installed one stays. The registry is not asked.
- __Confirm or fall back__ (`settleUpdatedAddons`, after the load pass): loaded, or switched off so there was nothing to try, `confirmUpdate` writes the lock without `previous` first, then removes `.previous-<slug>` and the old tarball best-effort. Until that write, the previous release is whole, so a failed write or a crash leaves either the new release confirmed or a complete fall-back, never a lock naming deleted files. Not loaded, `rollBackUpdate` sets the new folder aside as `.rejected-<slug>-<time>`, restores `.previous-<slug>`, deletes the new tarball and restores the lock entry, so the next start runs the previous release, verified from its kept tarball. Admins are told, and the fall-back is recorded. The previous release is not loaded in the same process, because the failed one cannot be unloaded.
- __A start that never confirmed__ (the process stopped during the load pass): the next start finds `previous` in the lock and falls back before anything loads, so a release that crashes the process cannot crash every start.

The decided behaviour, and what is not built yet, is in [the addons developer guide](../guides/addons-developer-guide.md#installed-add-ons).
