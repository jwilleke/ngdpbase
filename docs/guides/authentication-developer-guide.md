# Authentication developer guide

What a developer has to know to change how users sign in. Who may do what once signed in is [security-developer-guide.md](security-developer-guide.md); the design history, open plans and YourPHR's needs are in [planning/authentication.md](../planning/authentication.md).

## Provider docs

Every sign-in method is a provider registered with [AuthManager](../managers/AuthManager.md) (the methods, and the one door routes call). Each has its own page:

- Signing users in
  - [PasswordAuthProvider](../providers/PasswordAuthProvider.md) — username and password, checked against the hash on the user record
  - [PasskeyAuthProvider](../providers/PasskeyAuthProvider.md) — passkeys (WebAuthn); a passkey alone signs in at AAL2, phishing-resistant
  - [MagicLinkAuthProvider](../providers/MagicLinkAuthProvider.md) — an emailed single-use sign-in link
  - [OidcAuthProvider](../providers/OidcAuthProvider.md) — sign-in through any outside OpenID Connect provider, by an identity connected to the account: what it may do, the flows and their checks
    - [Google](../providers/OidcAuthProvider-Google.md) — the `google` preset, and registering the site in the Google Cloud console
    - [Microsoft](../providers/OidcAuthProvider-Microsoft.md) — the `microsoft` preset (personal accounts only), and registering the site in Microsoft Entra
    - [Apple](../providers/OidcAuthProvider-Apple.md) — the `apple` preset: a client secret the site signs, the POSTed callback, and registering with Apple
    - [authentik](../providers/OidcAuthProvider-Authentik.md) — a self-hosted authentik as an entry with its own issuer (no preset)
  - [CloudflareAccessAuthProvider](../providers/CloudflareAccessAuthProvider.md) — trusts Cloudflare Access's `cf-access-jwt-assertion` header when the site sits behind it
- Requests from clients (bearer tokens; never a session)
  - [AgentTokenAuthProvider](../providers/AgentTokenAuthProvider.md) — an agent token a user minted, delegating part of their own authority
  - [OidcBearerAuthProvider](../providers/OidcBearerAuthProvider.md) — access tokens from this site's own OpenID Connect server, for apps a user allowed
  - [AuthentikBearerAuthProvider](../providers/AuthentikBearerAuthProvider.md) — an authentik-issued token held by a headless client
- The contract and what sign-in methods keep
  - [BaseAuthProvider](../providers/BaseAuthProvider.md) — the interface every sign-in method implements
  - [BaseCredentialsProvider](../providers/BaseCredentialsProvider.md) and [FileCredentialsProvider](../providers/FileCredentialsProvider.md) — the credentials store: passkeys, verified addresses, connected outside identities, as signed rows
  - [FileOidcAdapter](../providers/FileOidcAdapter.md) — storage for this site's own OpenID Connect server ([OidcManager](../managers/OidcManager.md)): grants, sessions and tokens of apps users sign in to with this site

For users signing in, the shipped help page [Signing In With Another Account](../../required-pages/349c67da-871c-40a5-8581-89bad4988970.md) is the user-facing counterpart of the outside providers: connecting one on the profile, signing in with it, and the email step.

## Standing rules

- __AuthManager is the one door.__ Routes call `AuthManager`, never a provider. Every sign-in method is a registered `AuthProvider` (`registerProvider`), so a new method is a provider, not a route. This covers every check of a secret, not only a sign-in: re-checking a password before a change, an API key, a token. The provider is the connection to its method and owns the check; where the method's data lives (the password hash on the user record) is the storing manager's (operator, 2026-10-11).
- __What is offered is configuration.__ `ngdpbase.auth.factors` lists the methods a site offers, one entry per provider: `authproviderid`, `primary` (can start a sign-in), `amr` / `aal` / `acr`, `enabled`. Configuration may lower what a provider's code declares, never raise it. `getFactors()` is what is available; `assess(factors)` what a set of satisfied factors amounts to, by NIST SP 800-63B: an email link never lifts a sign-in above AAL1, and only WebAuthn is phishing-resistant.
- __The session records how it signed in.__ Every sign-in path writes `req.session.signIn` (`signInRecord()`): the provider, each factor with its time, and `amr` / `aal` / `acr`. Step-up and UserInfo read it there. A delegated credential (agent token, share, app token) never starts a session and never satisfies step-up.
- __What is required is per role.__ Each role in `ngdpbase.roles.definitions` may carry `required-aal` (1–3). A user must meet the highest among their roles. `admin` and `user-admin` ship at 2; every other role at 1; `anonymous` has none.
- __A role above the sign-in steps down; nobody is locked out.__ In a session signed in below a role's level, the user acts without that role (`rolesAtSignIn`) and a banner says how to get it back. `profile-manage` and `account-security` stay, so the profile, where a passkey is added, is always reachable. When the level cannot be reached at all, see the next section.
- __Sensitive actions ask for a fresh sign-in.__ A permission entry marked `"step-up": true` needs a factor satisfied within `ngdpbase.auth.step-up.max-age-minutes` at the level the user's roles require. The PDP decides it inside `hasPermission`; a control's visibility asks `holdsPermission`, which leaves step-up out ([#1635](https://github.com/jwilleke/ngdpbase/issues/1635)). Step-up itself is AuthManager's ([#1758](https://github.com/jwilleke/ngdpbase/issues/1758)): the freshness rule (`stepUpNeeded`, which the PDP asks), the answer to a refused request (`askForFreshSignIn`, used by core routes and `ApiContext` alike), re-authentication (`completeReauth`) and every step-up record (`recordReauth`). An add-on marks its own permission the same way, in its `config/default-config.json`: permission definitions merge per entry, so it neither touches core's list nor another add-on's. The window is one site-wide value, shipped at 60 minutes (operator, 2026-10-18; it was 15); there is no per-action window, a site wanting "prove it now" sets 1, and 0 turns step-up off ([#1767](https://github.com/jwilleke/ngdpbase/issues/1767)).
- __Add-on permissions don't ask for step-up, for now__ (operator, 2026-10-18). A form an add-on shows loses its typed fields across the fresh sign-in, so an add-on leaves `"step-up"` off its permission entries and says so in its own docs. Core's six step-up permissions are unchanged. A form-field restore across step-up is not built.
- __A passkey belongs to the base URL's hostname.__ The relying-party id is `new URL(ngdpbase.application.base-url).hostname` (`relyingPartyFrom`, `src/providers/PasskeyAuthProvider.ts`); the port is ignored and the name (`rpName`) is only a label. Two instances on one hostname share one passkey scope: the browser offers either site's passkeys on both, and one made on the other fails. Give each instance its own hostname (`*.localhost` works over http). Changing an instance's hostname orphans every passkey enrolled on it, with no warning: users sign in another way and enrol again ([#1878](https://github.com/jwilleke/ngdpbase/issues/1878)).
- __Every sign-in completes in one step:__ `AuthManager.completeSignIn(req, result, how)` ([#1758](https://github.com/jwilleke/ngdpbase/issues/1758)). Password, passkey, second factor, email link and outside providers all end there: a new session (#1043), the identity, how it signed in (`session.signIn`), the password-change generation (#1482), the private stores (a handle already unlocked, or the password handed to the vault unlocker that the vault code registers with `setVaultUnlocker`), one audit record of the completed sign-in naming how, the count on the account, and a pending outside identity carried across the new session, never connected (#1743, below). `authenticate()` records failures and re-checks; a successful sign-in is recorded only here. A route saves the session and answers, going to the returned `next` when it is set (the page that asks whether a pending outside identity is the user's), nothing more. A new sign-in method calls `completeSignIn` with `returnTo` (where it was going) and honours `next`.
- __A second step follows every sign-in that has only a password behind it__ ([#1532](https://github.com/jwilleke/ngdpbase/issues/1532), operator 2026-10-22). When the account has a usable second factor, `AuthManager.needsSecondStep(result)` holds a password typed here and an outside provider's sign-in at AAL1 as a pending sign-in (`beginTwoStep`), never a session; not an email link (same inbox), not a passkey or a provider at AAL2. A new sign-in method asks `needsSecondStep` before `completeSignIn`. The approval message and page say the site, the time in the user's zone, the browser, the IP address and roughly where (`approximateLocation`: Cloudflare's headers only when `ngdpbase.server.behind-cloudflare`, else an operator's GeoLite2 City file, else nothing; never an outside lookup), with every value escaped in HTML. Each step is recorded as a `signinapproval-*` event tied to the pending sign-in's `id`, never its handle or the link token. Details: [AuthManager](../managers/AuthManager.md#two-step-sign-in-1523).
- __A sign-in ends with the stored username, never the typed one__ ([#1882](https://github.com/jwilleke/ngdpbase/issues/1882)). Usernames are looked up normalized ([#1436](https://github.com/jwilleke/ngdpbase/issues/1436)), so "ADMIN" finds admin's record and admin's password; carried on as typed, it was a second identity with no roles and a personal vault of its own. A provider returns the name on the account record (the password check reads it from `getUser`; an account a provider creates is named by what `createUser` returned). AuthManager then holds every sign-in to it at each door a sign-in passes, with one rule, `storedUsername`: `authenticate` (for a sign-in method, one with an `ngdpbase.auth.factors` entry; before `userMayUseProvider`, so second factors, the vault unlock and the audit see the stored name), `beginTwoStep` and `completeSignIn`. A name no stored account has is refused: `authenticate` fails, audited; `beginTwoStep` and `completeSignIn` throw before any session is made. A route uses `result.username` after `authenticate`, never the name from the form.
- __Turning an account off or deleting it goes through one step:__ `AuthManager.closeAccess(username, 'disable' | 'delete', ctx)`, called by `UserManager` ([#1765](https://github.com/jwilleke/ngdpbase/issues/1765)). Both end every session in the live session store, the one express-session reads: `UserManager.deleteUserSessions(username, reason)` lists the store (through `SessionStatsManager`, which holds it), ends each of the account's sessions through `endSession` with the reason `account-deleted` or `account-disabled`, and destroys it, so the admin sessions list no longer shows it ([#1937](https://github.com/jwilleke/ngdpbase/issues/1937); before, only the user provider's own session list was cleared, which nothing reads). Disable leaves tokens, app grants and shares to be refused live (their owner is inactive) and keeps the credentials, so turning the account back on restores them. Delete revokes the agent tokens, app grants and shares, and removes the account's credentials-store rows: a row names its account by username, so one left behind would sign in to a new account later created with the same name. A new kind of access an account can hold is closed here, never by its own route.
- __Every way a session ends goes through one door:__ `endSession()` in `src/utils/sessionEnd.ts` drops the session's private-store keys and records `authentication-logout` with the reason ([#1670](https://github.com/jwilleke/ngdpbase/issues/1670)): `logout`, `idle-timeout`, `max-age`, `password-changed`, `superseded`, `account-deleted`, `account-disabled`.
- __A signed-in session belongs to the account it signed in to, checked on every request__ ([#1937](https://github.com/jwilleke/ngdpbase/issues/1937)). A username outlives its account, so every sign-in binds the session to the account itself: `stampSessionGeneration` writes `session.accountCreatedAt` (the account's `createdAt`) beside the password-change generation (#1482). `checkSessionAccount` in `src/utils/sessionAccount.ts`, called by the session middleware in `app.ts`, ends the session through `endSession` when no account has the name (`account-deleted`), when the account by that name is another one (a different `createdAt`, or, for a session signed in before the binding existed, created after `signedInAt`: also `account-deleted`), when the account is turned off (`isActive === false`, `account-disabled`), or when the password changed since (`password-changed`). An older session that still belongs to its account is bound on its next request. So a session the store close missed is still refused, and a new account with an old name never inherits a session. At startup `UserManager.endStaleSessions` applies the same rule to every session in the store and destroys those it ends, so leftovers from before this rule do not wait for their next request. A new reason an account stops owning its sessions goes in `checkSessionAccount`.
- __A signed-in session ends at two limits, checked in one place__ ([#1767](https://github.com/jwilleke/ngdpbase/issues/1767)). `ngdpbase.session.idle-timeout-minutes` (shipped 10080, 7 days; a role's `idle-timeout-minutes` may only shorten it, [#1546](https://github.com/jwilleke/ngdpbase/issues/1546)) ends one with no request for that long; `ngdpbase.session.max-age` (shipped 2592000000 ms, 30 days) ends one that long after it signed in, however active. `checkSessionLimits` in `src/utils/sessionLimits.ts`, called by the session middleware in `app.ts`, decides both on every request, and the end goes through `endSession` with the reason `max-age` or `idle-timeout`. The cap counts from `session.signedInAt`, which only `completeSignIn` writes, on the new session; a re-authentication never moves it. The cookie and the file store roll forward on use (express-session re-issues the cookie whenever the session changes; the store expires a session after its last access), so they are never the cap: a sign-in sets its cookie to the cap so the cookie never ends a session sooner, and a session nobody signed in to lives `ngdpbase.session.anonymous-max-age` (shipped 86400000 ms, a day; never longer than `max-age`, read at startup), so the store does not hold a month of one-visit sessions. A new limit goes in `checkSessionLimits`, not in a route.
- __A session cookie the browser will never get is reported, never silent__ ([#2071](https://github.com/jwilleke/ngdpbase/issues/2071)). With no `ngdpbase.session.secure` in the operator's file the cookie is secure exactly when `NODE_ENV` is `production` (`resolveSessionSecurity`, unchanged), and express-session sends no `Secure` cookie on a request Express sees as plain http after `trust proxy`, so every POST meets a fresh session and the CSRF middleware refuses it. `sessionCookieWithheld(req)` (`src/utils/sessionSecurity.ts`) is that one check: `req.session.cookie.secure` true and `req.secure` false. When the cookie is secure, `app.ts` runs it on every request after the session middleware and calls `UserManager.reportSessionCookieWithheld()`, which, once per process, logs an error, marks UserManager needs-attention (key `ngdpbase.session.secure`) and notifies administrators; every later call is one boolean. The CSRF refusal and the login pages show `SESSION_COOKIE_WITHHELD_MESSAGE`, the one wording, when the same check is true. The health routes are registered before the session middleware, so plain-http probes never trigger it.
- __Sign-in throttling stays in memory__ (operator, 2026-10-11, [#1767](https://github.com/jwilleke/ngdpbase/issues/1767)). `LoginThrottle` counts failures in each server process, so several copies of the server each allow their own `max-attempts`. At startup `throttlePerCopyWarning` logs one warning when pm2 runs more than one copy.
- __One email, one account__ ([#1748](https://github.com/jwilleke/ngdpbase/issues/1748)). `UserManager` refuses to save an email another account already has, on create and on change, on every path (registration, profile, admin, outside sign-in). It's not a setting. Emails are compared trimmed and in any case, with no provider rules: `smiths+alice@gmail.com` and `smiths+bob@gmail.com` are different addresses. Accounts without an email are allowed. `getUserByEmail` returns nobody for an email two accounts already share (saved before the rule), and the startup check reports any such pair (manager degraded, log, admin notification) until an admin gives each account its own. The failure reason is `email-taken`; registration shows its safe message, and the profile page never names the other account.
- __An outside client's key is an agent token, never a shared key__ (operator, 2026-10-11, #1759). A user mints it, scoped to what the client needs; it is checked through AuthManager like any token, the request runs as that user within the token's scope, and deleting the token stops the client. Tokens arrive as `Authorization: Bearer`; the one exception is Dawarich, an Immich client, which sends its key in `x-api-key` on its two routes only (`isDawarichApiKeyPath`). To connect Dawarich: mint an agent token scoped to `media-read` on your profile and enter it as Dawarich's Immich API key (the old `ngdpbase.dawarichCompat.apiKey` setting is gone).
- __One list of what a user delegated, one door to revoke it__ ([#1764](https://github.com/jwilleke/ngdpbase/issues/1764), operator, 2026-10-11). Profile → __My tokens and devices__ lists the user's agent tokens and the apps and devices they approved through this site's own sign-in server (`AuthManager.listDelegations`). Each row says which kind it is: __fixed__ (ends on its date: an agent token, or an app holding no refresh key) or __refreshable__ (renewed automatically with a new key each time: an app or device holding a refresh key), with its end date or last renewal, what it may do, and Revoke. Every Revoke goes through `AuthManager.revokeDelegation(ctx, username, kind, id)`: the list, `DELETE /api/tokens/:id`, `POST /profile/apps/:grantId/revoke`, the admin user page and `closeAccess`. Your own needs `account-security` (so step-up); anyone else's `user-edit`. It ends only a live item of that account, and the owning manager audits it as by whoever revoked it, naming the owner (`token-revoke`, `oidcgrant-revoke`). A new kind of delegated credential joins this list and this door, never a card and route of its own.
- __Every signed-in user except demo-admin may mint an agent token; extending one is `token-extend`__ (operator, 2026-10-09, approved 2026-10-12, [#1734](https://github.com/jwilleke/ngdpbase/issues/1734)). `token-mint` is granted in every signed-in role's policy except `demo-admin` (operator, 2026-10-12: a demo visitor changes nothing lasting), never to `anonymous`; both it and `token-extend` are step-up. `token-extend` ships to admin only and is grantable. `AgentTokenManager.extend` moves a live token's expiry later for its owner only, never past now + `ngdpbase.auth.agent-token.max-ttl-hours`, keeping the token string and scopes; it is audited (`token-extend`, old and new expiry) before the expiry moves. A delegation never carries either permission (`src/utils/delegation.ts`), so a token can neither breed nor keep itself alive. The Extend button lives in the row actions of __My tokens and devices__ (`views/_delegations.ejs`, local `canExtend`), only on the viewer's own fixed agent tokens and only when they hold `token-extend`; such a token is labelled __Extendable__ instead of __Fixed__ (operator, 2026-10-13). It calls `POST /api/tokens/:id/extend` and follows its `reauth` link for step-up. Agent tokens stay off per site until `ngdpbase.auth.agent-token.enabled`. Details: [AgentTokenManager](../managers/AgentTokenManager.md#extending).
- __A proxy grant is a record, made through one door__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 1, operator decisions 2026-10-12). A user lets another act for them with `AuthManager.grantProxy`; `revokeProxy` and `listProxyGrants` (both sides: grants made, grants received) are the only other doors, and `closeAccess` ends every grant a deleted account is on, either side. All three refuse while `ngdpbase.auth.proxy-access.enabled` is false (the default). A grant may carry any permission the user represented holds now, and nothing else (delegate, not grant: the agent-token check, `lackingScopes`); one including `proxy-grant` lets the proxy give others access too (`mayRedelegate`, for the screen's warning). A token or an app never carries `proxy-grant` (`refusedDelegatedScope`, beside `token-mint` and `token-extend`). Making one on your own account needs `proxy-grant` (step-up); an administrator making or ending one for someone also needs `user-edit`, and an administrator's grant is marked `vault: 'never'`: it never carries a copy of the user's vault key, which only the user can add, with their store unlocked. `expiresAt` is optional; without it a grant lasts until revoked. A grant is a signed `proxy` row of the credentials store, never a sign-in method: the credential methods neither list nor change one. `proxy-grant` and `proxy-revoke` are recorded first, with `user` the user represented and a top-level `actor` naming who acted.
- __The proxy screens are views over the grant doors, hidden while proxy access is off__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 7). The profile's __Proxy access__ card (`_proxy-grants.ejs`, `_proxy-grant-form.ejs`) lists the grants a user made, with Revoke, and a give form (`POST /profile/proxy-access`, `POST /profile/proxy-access/:id/revoke`); the admin user page reuses both partials (`POST /admin/users/:username/proxy-access[/:id/revoke]`, `user-edit` then `proxy-grant`, so a fresh sign-in, recorded with the administrator as actor). Each route answers Not Found while `ngdpbase.auth.proxy-access.enabled` is false, asks `proxy-grant` at the door (the step-up path), and leaves every decision to `grantProxy` / `revokeProxy`. The form offers only `AuthManager.proxyGrantOptions(ctx, owner)`: the grantable catalog permissions the owner holds now, by their `label`, so it shows nothing `grantProxy` would refuse. Ticking `proxy-grant` shows the decided warning "Jim will be able to give other people access to your account." (the name picked) An administrator's form never offers `vault-proxy`, and `grantProxy` refuses it on a grant made for someone else (vault access is added only by the user). The end date goes out as the end of the chosen day in the viewer's own time zone; listed dates use `<time data-local-time>`. The user is picked with the shared user typeahead (`audience-typeahead.js`, `data-audience-field` / `data-audience-single`). The header shows an __Act as__ picker (`_acting-for-picker.ejs`, `res.locals.actingForPicker` from `actingForChoices`) only to someone a live grant names, posting to the slice 4 switch door; the "Acting for … · Switch back" banner stays.
- __Every audit row done under a proxy names both people__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 3, operator decision 2026-10-12). `user` is the user represented, the account acted on (as with agent tokens); a top-level `actor` is the proxy who actually did it, with `metadata.delegated: 'proxy'` and `proxyGrantId` joining the row to its grant. One place builds it: `proxyAttribution(claim)` in `src/utils/proxyClaim.ts`, read by `actorOf` (requests), `attributedTo` (jobs), `PolicyInformationPoint.auditDenial` (refusals, including media) and the content builders (`viaProxy` beside `viaToken`). A row with no proxy has no `actor` field. The audit search and `/admin/audit` filter on it (`?actor=`). `npm run lint:audit-attribution` holds every emitter to it.
- __A proxy acts within grant ∩ the user represented ∩ the proxy, decided by the PDP__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 2). The subject is the user represented (`username`, `roles`) carrying `viaProxy = { kind: 'proxy', grantId, actor, scopes }` (`ProxyClaim`); `kind: 'impersonation'` is reserved for [#1763](https://github.com/jwilleke/ngdpbase/issues/1763) and admits nothing. `PolicyDecisionPoint.ceiling` refuses, in order: a subject also carrying a token or share (`proxy_combined_deny`); any kind but `proxy` (`proxy_kind_deny`); a grant not in force, re-read on every decision through `AuthManager.liveProxyGrant` (revoked, past its end date, proxy access off, naming another user or actor, narrower than the claim's scopes, or the user represented no longer an active account: `proxy_revoked`); an action not in the claim's scopes (`proxy_scope_deny`); an action the actor does not hold now (`proxy_actor_deny`, asked as `holds`, policy alone). Passing is not an allow: policy then runs for the user represented. The page door, the list filter (`filterAccessiblePages`) and the media door ask the same ceiling (`carriesCeiling`). Step-up treats a proxy as a user at the keyboard, not a delegation: the subject's `signIn` and `aalCap` are the actor's (the session's), so the actor's own fresh sign-in counts. A job started under a proxy keeps the claim (`JobContext.viaProxy`), so it never runs as the user represented unbounded.
- __Whom a session acts for is the session's choice, re-checked on every request, built in one place__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 4). `session.actingFor` holds a grant id, set and cleared only by `AuthManager.switchActingFor(req, grantId | null)` behind `GET`/`POST /account/acting-for` (`ACTING_FOR_PATH`, CSRF-guarded form post). The authority to switch is the signed-in interactive session and the grant itself: live, naming the session's user as proxy, the represented account active. Switching back is always allowed. `session.username` stays the user who signed in; only the subject changes. `AuthManager.subjectActingFor(req, self)` is the one builder of the proxy subject, called only from the session middleware in `app.ts` that sets `req.userContext`; `ApiContext` and `WikiContext` take it from there unchanged. It re-reads the grant live on every request; a grant revoked or expired mid-session, an inactive account, or proxy access turned off drops the session back to the user (`actingFor` cleared, recorded as `proxy-switch` with reason `grant-ended` or `proxy-access-off`), so no request ever acts on a dead grant. The proxy subject carries the actor's `signIn` and `aalCap`, the represented user's roles held at the actor's sign-in level (`rolesAtSignIn`), and no `privateStoreHandle` (the key bag is the actor's; a grant's key copy is reached through `viaProxy.keyHandle` only, below). An agent token or an app never acts for anyone: the switch refuses a bearer request (`req.bearerAuth`), the bearer middleware rebuilds the subject from the token with no claim, and `subjectActingFor` never turns a subject carrying a token or share into a proxy. `completeSignIn` sends a user a live grant names to the choice page first (`next`), carrying where they were going (`returnTo`); a sign-in never starts acting for anyone unasked. Every session end (`endSession`: sign-out, idle, max age, password change, a new sign-in) drops the choice. While a session acts for someone the private-store unlock page and banner do nothing (`privateStoreUnlockState` reports unlocked), and every page shows "Acting for … · Switch back" (`res.locals.actingFor`). Each switch is recorded as `proxy-switch` (`chosen`, `switched-back`, `grant-ended`, `proxy-access-off`), `user` the user represented and `actor` the user signed in.
- __Encrypted vaults open to a proxy only through a key copy the owner made__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 5, operator decisions 2026-10-12). Each user has a P-256 key pair (`UserKeyEnvelope.personKey`: the public half readable, the private half wrapped under their own KEK), made at enrolment (`createUserKeys`) or, for someone enrolled earlier, the first time their store is unlocked. A grant the owner makes for themselves with `vault-proxy`, while their store is unlocked, seals a copy of their KEK to the proxy's public key (`sealKekCopyFor`, the share lockbox's ECDH + HKDF + AES-GCM, no other crypto); the sealed copy lives in the grant's credentials row (`keyCopy`), never on the grant as listed or recorded, and the grant reads `vault: 'copy'`. `grantProxy` refuses, in plain words, `vault-proxy` from an owner whose encrypted store is locked, to a proxy with no key pair yet, from an administrator (`vault: 'never'`), and from a proxy re-delegating; an owner with no encrypted store gets `vault: 'none'` (unencrypted vaults only). `AuthManager.vaultGrantBlocked(ctx, owner)` gives the same reason to the give form, which disables the choice and shows it. `subjectActingFor` opens the copy into the actor's own key bag when the actor's store is unlocked (`openKeyCopy`: their KEK unwraps their private key, which opens the copy), once, recorded as `proxy-switch` reason `vault-opened` naming both users; the subject's claim then carries `keyHandle`, and `dekFor` / `unlockedStoreIdsFor` answer from the copy only when the claim is a `proxy` claim carrying `vault-proxy`, the bag is the claim's actor's, and the copy was opened under that grant for the user represented. The copy is wiped on switching back or to someone else, when a grant is found dead on a request, on revoke or account deletion (`dropKeyCopiesOfGrant`, every session), and with the actor's own keys at sign-out or session end (`lockPrivateStores`). Revoking deletes the sealed copy with the row. `kekFor`, `hasUnlockedKey` and `userIndexFor` stay the owner's alone: a proxy never creates a vault or re-wraps keys. A password change or a reset with the recovery words leaves the KEK as it is, so copies stay valid; there is no KEK rotation today, and one must turn every copy of that KEK stale (drop the copies, `vault: 'none'`) rather than leave a copy that opens nothing.
- __An outside sign-in signs in a connected identity, nothing else__ ([#1743](https://github.com/jwilleke/ngdpbase/issues/1743), decided 2026-10-10). `OidcAuthProvider` is one class with one registered instance per enabled entry of `ngdpbase.auth.oidc.providers` (`oidc:<name>`; the old `ngdpbase.auth.google-oidc.*` keys are the `google` entry). The identity is issuer + subject, a credentials-store row of kind `identity` (subject `iss#sub`); each belongs to exactly one account, and it is a way in only while its provider is enabled. Email never matches or signs anyone in, groups and roles claims are never read, no access or refresh token is kept, and a refusal never says whether an account exists. Connecting is the signed-in user's own `account-security` change (`startConnect` → `connectIdentity`, step-up applies); disconnecting is `removeCredential` under the last-way-in rule. Every connection is made in one place, `attachIdentity`, and audited as a credential added with how it happened. Every outbound request (discovery, keys, the code exchange) goes through `guardedFetch`; a client secret, and Apple's signing key (`private-key`), are only environment references (`$NAME`). A provider with no `ngdpbase.auth.factors` entry is a primary method at AAL1.
- __An outside provider's own second factor counts only when the admin trusts it__ ([#1633](https://github.com/jwilleke/ngdpbase/issues/1633), operator 2026-10-05). The one switch is the provider's entry in `ngdpbase.auth.oidc.providers`: `"trust-mfa": true`, off by default and read at each sign-in (the old `ngdpbase.auth.google-oidc.*` keys have none, so off; operator decision 2026-10-12 kept it as the only switch). `"amr": ["trust"]` in `ngdpbase.auth.factors`, the earlier plan, is inert (`lowered` drops it): the shipped factors list carries it, so honouring it would have trusted Google on every install. The provider passes the verified ID token's `amr` and `acr` on unread (`AuthResult.reported`); AuthManager keeps only well-formed values (an `amr` that is not an array is `[]`, bounded) and maps them in one place, `outsideLevel`, for every outside provider. Untrusted: AAL1, no `amr`, whatever was sent. Trusted (operator 2026-10-12): the report is taken as given, to whatever level it shows — the RFC 8176 values only, at __AAL3__ and phishing-resistant (`phrh`) when a hardware-bound key (`hwk`) comes with a second factor or user verification (`mfa`, `user`, or a second factor type by the rule `assess` applies to this site's own factors: `hwk` + `pin`, `hwk` + `fpt`, `hwk` + `pwd`; not `hwk` alone, not `hwk` + `otp`); at __AAL2__ when they say multi-factor otherwise — `mfa`, or two factor types by `assess` (`pwd` + `otp`, `swk` + `pin`, `pwd` + `sms`; not `pwd` + `kba`); an SP 800-63C `acr` raises the level to the one it states (`http://idmanagement.gov/ns/assurance/aal/2` is AAL2, `…/aal/3` is AAL3) but is never phishing resistance; AAL1 otherwise. The mapped level is the sign-in's satisfied factor, so roles (`rolesAtSignIn`) and step-up (`stepUpNeeded`, within the window) read the same level. What is offered, `reachableAal` and `aalReachFor` are unchanged (AAL1): a provider may not report MFA on the next sign-in, so it is never counted as a way the account can reach AAL2, and a role's level stays capped by the account's own reach. The sign-in's `authentication-success` record carries `metadata.reported` (`amr`, `acr`, `trusted`), trusted or not — never a token — so an admin can see what a provider sends before trusting it.
- __Tokens and devices a proxy approves belong to the user represented__ ([#1762](https://github.com/jwilleke/ngdpbase/issues/1762) slice 6, operator decisions 2026-10-12). Someone acting for a user may mint an agent token or approve a device for them only when the grant allows it, with no new permission: `token-mint` for a token, `account-security` (the device-approval permission, `DEVICE_APPROVAL_PERMISSION`) for a device. Both are asked of the PDP with the proxy subject, so the grant must carry it and both users must hold it, and the step-up is the proxy's own sign-in. `AgentTokenManager.mint` asks `token-mint` itself as well as at the route, and checks every scope with the same `permits`, which under a proxy is grant ∩ the user represented ∩ the proxy; the never-delegated permissions stay refused (`refusedDelegatedScope`). A device asks `OidcManager.proxyApprovalRefusal(subject, scope)` for each API permission it requests, the same intersection, refused in plain words. While a session acts for someone, the sign-in bridge signs the provider in as the user represented (`OidcRoutes` `signedInAs`) and approves only a device: an app sign-in is refused with "Switch back to yourself to sign in to an app." The credential belongs to the user represented and records the proxy: a token's `approvedBy` and `proxyGrantId`; for a device, a `ProxyApproval` row beside the provider's grant (the provider rewrites a grant from its own fields, so one added to it would be lost), written by `OidcManager.finishConsent`. Either works only while that grant is in force (`liveProxyGrant` at every use: revoked, past its end date, or proxy access off, and it stops), and ending the grant (`revokeProxy`, or `closeAccess` deleting either account) revokes them through the one revoke loop (`endDelegationsWhere`, the loop `closeAccess` uses), before the grant row goes. "My tokens and devices" says "Approved by jim (acting for you)" on such rows, and the admin user page "(acting for mom)"; a proxy acting for someone sees their list when the grant carries `account-security`. The audit rows name both users: `token-mint` and `token-revoke` forward `viaProxy`, `oidcgrant-revoke` spreads `proxyAttribution` of whoever revoked, and a device approval is recorded as `oidcauthorize-allow` with reason `approved-by-proxy`, `user` the user represented and `actor` the proxy. `AgentTokenManager.revoke` and `OidcManager.revokeGrant` take the subject who revoked, never a username.
- __A POSTed callback is relayed, never finished as a POST__ ([#1743](https://github.com/jwilleke/ngdpbase/issues/1743) slice 4b). Apple returns with `response_mode=form_post`: a cross-site top-level POST, which carries none of this site's `SameSite=Lax` cookies, so neither the session nor the `ngdp_oauth_state` binding (#1630) is there. `src/middleware/outsideCallbackRelay.ts` is mounted in `app.ts` before the session and CSRF middleware, on `POST /auth/oauth/:name/callback` only, and only for a provider `AuthManager.callbackIsPosted` names (a preset with `responseMode: 'form_post'`). It answers with a 303 to the GET callback carrying `code`, `state` and `error`, nothing else; the GET brings the Lax cookies and the ordinary finish runs. Being before the session, it starts no session whose cookie would replace the user's own. Any other POST to a callback falls through to CSRF and is refused. Do not exempt a path in `csrf.ts`, and do not finish a sign-in on the POST: the browser binding is the protection against login CSRF. Apple's client secret is a JWT the provider signs per exchange (`SignedClientSecret`), not a shared secret.
- __An identity connected to no account goes to the email step, or gets an account__ ([#1743](https://github.com/jwilleke/ngdpbase/issues/1743) slice 3, decided 2026-10-11). `AuthManager.finishOutsideSignIn` decides every outside callback; the route only answers. A verified identity that no account has connected is held in the session as a pending connection (provider, `iss#sub`, the verified email or `''`, the provider's name, 5 minutes; one at a time, a new one replaces the old), and the sign-in page says "Sign in to connect your *Provider* account (*email*)" with a way to cancel (`POST /login/connect/cancel`). __A sign-in never connects it by itself__ (review, 2026-10-11): on a shared computer the waiting identity may be someone else's, and connecting it would let them sign in as the next user. `completeSignIn` carries it across the new session and sends the user to `GET /login/connect/confirm`, which asks "Connect the *Provider* account (*email*) to your account *username*?" and warns that anyone who can sign in to it will be able to sign in here. Only Connect (a CSRF-protected POST) calls `confirmPendingConnection`, which checks again (signed in, not expired, provider enabled and allowed for the account, not connected elsewhere) and connects through `attachIdentity`. Don't connect drops it and goes where the sign-in was going; ignored, it expires; signing out drops it (`endSession`). Email never signs anyone in and is never looked up, so the page is the same whether or not an account has that email. An account is created instead only when `ngdpbase.auth.oidc.auto-provision`, the provider's own `auto-provision` and `ngdpbase.application.registration` are all true and the provider verified the email: by magic-link auto-provisioning's path (`deriveUsername`, `UserManager.createUser`, which records it; no password, registration's default roles, none from the provider), then the identity is connected and the user signed in through `completeSignIn`. The same rule, asked for every enabled provider, is `outsideSignUpOpen()`: the header's Register button counts it as open sign-up and leads to the sign-in page, where the provider buttons are. If the identity cannot be connected, the account just created is deleted through `UserManager.deleteUser` (which closes its access) and nobody is signed in, so no account is left with no way in. An email that already belongs to an account creates nothing: the email step, with registration's `email-taken` message.
- __The sign-in page labels each method; an outside provider's button has one rendering path__ ([#1781](https://github.com/jwilleke/ngdpbase/issues/1781), operator, 2026-10-12). `views/login.ejs` shows a headed section per method that is on, in this order: Username and password, Passkey, External provider; the headings separate them, with no "or" lines (operator, 2026-10-12). The passkey section starts hidden and `passkey.js` shows it (`data-passkey-section`) where the browser supports passkeys. Every outside provider's button, on the sign-in page and the profile's Connect, is drawn by `views/_outside-provider-button.ejs` from `OutsideProvider.icon`, which `resolveOutsideProviderIcon` resolves once at registration from the entry's `icon`: an `https://` image, a site path, or a Font Awesome name; anything else is refused with a warning and the default (by preset) shown. Views never decide a provider's icon by its name.
- __Passwords:__ scrypt at N=2^17, hashed off the request path (async), and re-hashed at the current cost on the next sign-in ([#1632](https://github.com/jwilleke/ngdpbase/issues/1632)). The check is `PasswordAuthProvider`'s, through `AuthManager.authenticate`; `UserManager` keeps the stored hash and hands it only to that check ([#1758](https://github.com/jwilleke/ngdpbase/issues/1758)). AuthManager audits every sign-in method's check itself, with where it came from (`AuthAttempt`), and counts a sign-in (not a re-check) on the account; routes write no audit record for a check. The minimum length is `ngdpbase.user.security.password-min-length` (6).
- __A new user without a password is invited, once__ ([#2049](https://github.com/jwilleke/ngdpbase/issues/2049), operator 2026-10-24, option A). `AuthManager.inviteUser(ctx, username)` emails a one-time link (`/invitation?t=…`) to an account with an email, no password and no sign-in yet; sending, resending and cancelling (`cancelInvitation`) need `user-create`, asked of the PDP with the caller's context, which an add-on hands on from its request. The link is a signed `invitation` row of the credentials store holding only the token's SHA-256, so it survives a restart; it lasts `ngdpbase.auth.invitation.ttl-days` (shipped 7), and a new one ends the old. Opening it changes nothing (`invitationFor`, scanner-safe, as the magic link); the page's CSRF-guarded button calls `useInvitation`, which spends the row first (the store's in-memory delete is the single-use gate) and then signs in through `completeSignIn` at AAL1 as an email link (`amr` `email`, method `invitation`), so roles above AAL1 step down and the terms prompt comes first; it then goes to `/account/setup`: a first password (`UserManager.setFirstPassword`: the user themselves, `account-security`, only while the account has none), a passkey from the profile, the recovery words at a sealed store's door, and the terms. An invitation is not a sign-in method: no factor entry, never listed or changed by the credential methods, cancelled when the account is deleted. Email goes through `EmailManager.sendTo` with the caller's context; `invitationsUnavailable()` names why none can be sent (mail off or failing, no explicit base-url, no credentials store), the admin screen shows it, and a failed send removes the link again. `createUser` with no password now stores none rather than the hash of an empty string. Recorded: `invitation-send` and `invitation-cancel` (refuse, first), `invitation-use` and `invitation-expire` (continue); never the token.
- __A test account is an attribute, never a role__ ([#1805](https://github.com/jwilleke/ngdpbase/issues/1805)). `User.isTest` marks an account that holds test or synthetic data. Only an administrator sets it, through `createUser` / `updateUser` behind `user-create` / `user-edit`; `/profile` never accepts it. It grants nothing and no policy reads it: core marks it in `/admin/users`, shows the signed-in user a banner, and hands it to the host on the request's subject (`req.userContext.isTest`, `WikiContext.userContext.isTest`, the plugin ParseContext, `ApiContext.isTest`) and as the OIDC `test_account` claim (always a boolean, `profile` scope). The host decides what a test account may do. A change is a `user-edit` audit row carrying `isTest: { from, to }`.

## When a role's level cannot be reached

Operator rule (2026-10-08): __whenever there is no way to reach AAL2, AAL1 must be set__ — and the user is told, until they fix it, what to add.

| Situation | What a password sign-in gets | Where |
| --- | --- | --- |
| The site offers no AAL2 method (no explicit https `base-url`, so no passkeys), and the level is the shipped default | The roles, at AAL1. AuthManager reports `degraded` and says how to fix it | `effectiveLevels()`, [#448](https://github.com/jwilleke/ngdpbase/issues/448) |
| The site offers no AAL2 method, and the operator set the level in `app-custom-config.json` | The boot refuses and names the role | `checkRequiredAal()`, [#1523](https://github.com/jwilleke/ngdpbase/issues/1523) |
| The account's `allowedAuthMethods` exclude every AAL2 method | The roles, at AAL1 | `aalReachFor()`, [#1690](https://github.com/jwilleke/ngdpbase/issues/1690) |
| The account is allowed a passkey but has not enrolled one | The roles, at AAL1 — and a red banner on every page, which cannot be dismissed, saying to add a passkey, until one is | `rolesAwaitingEnrolment()`, [#1690](https://github.com/jwilleke/ngdpbase/issues/1690) |
| The account has an AAL2 method it can use | Roles above AAL1 step down for this session; the banner offers the passkey sign-in | `rolesAtSignIn()`, [#448](https://github.com/jwilleke/ngdpbase/issues/448) |

`aalReachFor(username)` gives `{ now, ifEnrolled }`: what the account's allowed, offered and (for a passkey) enrolled factors reach, and what they would reach once enrolled — both at least 1. `now` is carried on the request subject as `aalCap` and caps the level everywhere it is enforced: `rolesAtSignIn`, `requiredAalFor`, `stepUpNeeded` and the re-auth page. A factor that has to be enrolled before it counts is listed in `ENROLLED_FACTORS` in `AuthManager.ts`.

## Checklist for a new sign-in provider or factor

- 1 Write it as an `AuthProvider` and register it with `AuthManager.registerProvider` (an add-on registers it at load). No route calls it directly.
- 2 Declare its `amr`, `aal` and `acr` honestly, by SP 800-63B. Configuration can lower them; nothing can raise them.
- 3 Add it to `ngdpbase.auth.factors` (shipped, or in the add-on's `config/default-config.json`), with `primary` set only if it can start a sign-in on its own.
- 4 If it must be enrolled before it counts (a key, an app), add it to `ENROLLED_FACTORS`, store its rows through the credentials store, and offer enrolment on the profile's sign-in methods.
- 5 Its sign-ins produce a `signInRecord`, and success and failure are audited (`authentication-success` / `authentication-failed`) through `AuditManager.logAuthentication`.
- 6 Tests: the assessed level with and without it; a role at AAL2 kept or stepped down as the table above says; the audit records written. Sabotage each once.

Not yet: `CloudflareAccessAuthProvider` and `AuthentikBearerAuthProvider` (parked with [#1760](https://github.com/jwilleke/ngdpbase/issues/1760)) report nothing, so they stay AAL1; when they come back they set `reported` and get the same mapping. No `acr_values` is requested: the site reads what the provider sends. The shipped `"amr": ["trust"]` on the `oidc:google` and `cloudflare-access` entries of `ngdpbase.auth.factors` in `config/app-default-config.json` is inert and safe to remove (removing it changes no level); it is still there because a change to the default config needs the operator's yes. - [#1762](https://github.com/jwilleke/ngdpbase/issues/1762) — proxy access. Built: slice 1, the grant record; slice 2, the ceiling and the private-store rule; slice 3, every audit record naming both users; slice 4, choosing whom to act for, which turns it on; slice 5, encrypted vaults through a wrapped key copy; slice 6, tokens and devices approved by a proxy; slice 7, the screens (all above). Every slice is built. While a user acts for someone, the bridge leaves the provider's session signed in as the user represented after a device approval; signing in to an app as themselves afterwards is refused as "signed in as someone else" until that provider session ends (it fails closed). An app (not a device) cannot be approved for someone, by decision of this slice. A grant made with `vault-proxy` before slice 5 carries no copy (`vault: 'none'`): the owner gives access again, with their store unlocked, to share encrypted vaults. A grant made while the owner had no encrypted store likewise carries none, and does not gain one when they later make one. The private-store risk the plan found is closed: `mayActInPrivateContainer` admits a proxy only under a grant carrying `vault-proxy`, and an encrypted store opens to one only through its grant's key copy. The container rule reads the claim the subject carries, which `subjectActingFor` rebuilds from the live grant on every request. The unlock door, the one route that reads `session.privateStoreHandle` directly, does nothing while a session acts for someone. A proxy needs the action site-wide: holding it only inside one's own vaults (`vault-owner`) does not count toward acting for someone else. The "Jim acted for you" entries wait for the user's sign-in history page ([#1766](https://github.com/jwilleke/ngdpbase/issues/1766)), which does not exist yet.
