# Backup and restore guide

The one place that says how a site is backed up and restored, for operators and for developers, add-on authors included. Every statement here was checked against the code on master (v5.18.0 plus the database backup and restore of #1723, merged as 26a11b58) and against a backup taken on a throwaway instance on 2026-10-18, not against older documents; the parts added by [#1876](https://github.com/jwilleke/ngdpbase/issues/1876) slice 1 (attachment files, role membership, persons, organizations, public footnotes and comments, and the staged site restore) and slice 2 (the credentials store, the audit log, file-based job state, add-on files, encryption of every file under the backup key, and the "not restored" notification) were checked against their tests and a throwaway instance on 2026-10-19, and the whole-site restore on Admin → Backup ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945)) against its tests and E2E on a throwaway instance on 2026-10-21; the routes, Admin → Backup, the config keys and `BackupManager` were re-read against the code of v5.23.0 the same day. Since [#1985](https://github.com/jwilleke/ngdpbase/issues/1985) (2026-10-22) managers declare their folders and BackupManager does the archive, stage and apply work; that was checked against its tests, a backup written by v5.25.0 restored with the new code, and a whole-site restore E2E on a throwaway instance. Where something could not be checked it says "not verified".

In short: __a site can be backed up, and Admin → Backup can restore the whole site from a stored backup__ ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945)): the databases, the attachment files, role membership, persons, organizations, the footnotes and comments of public pages, the credentials store, the audit log, file-based job state, add-on files and the instance `.env`, staged together, all or nothing, and put in place at the next start ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876) slices 1 and 2). Pages, users and settings still have no staged restore, so a whole-site restore leaves them as they are and says so. With `NGDPBASE_BACKUP_KEY` set every file of a backup is encrypted under it. Until pages, users and settings restore too, a complete restorable site means a copy of the data folders, taken while the server is stopped, plus the keys kept somewhere else.

## Where a site's data lives

- __`FAST_STORAGE`__ is the instance data folder (falling back to the legacy `INSTANCE_DATA_FOLDER`, then `./data`; `src/utils/configFiles.ts` `instanceDataFolder`). It holds `config/app-custom-config.json`, `users/` (users and the credentials store), `roles/`, `persons/`, `organizations/`, `sessions/`, `logs/` (including `audit.log`), `search-index/`, `page-index.json`, `media-index.json`, `oidc/`, `shares/`, `notifications/`, `jobs/`, the database file `ngdpbase.db`, and the generated `.env`.
- __`SLOW_STORAGE`__ holds `pages/` (with `pages/vaults/`, the private stores), `attachments/`, `footnotes/`, `comments/` and, by default, `backups/`.
- __`<FAST_STORAGE>/.env`__ holds the keys the site generates for itself: `NGDPBASE_SESSION_SECRET`, `NGDPBASE_CREDENTIALS_KEY`, `NGDPBASE_BACKUP_KEY` (#1876: on first start when missing, as the session secret is, [bootstrap guide](bootstrap-developer-guide.md)), and the OpenID Connect provider's `OIDC_AUTH_SERVER_JWKS` and `OIDC_AUTH_SERVER_COOKIE_KEYS` when that provider is on; and what the operator puts there: `NGDPBASE_DATABASE_KEY` (never generated), mail and add-on secrets.
- Each path is a config key; the defaults are in `config/app-default-config.json`, and a site can move any of them.

## How a backup is made

- __By hand:__ Admin → Backup (`/admin/backup`) → __Create & Download Backup__ (`POST /admin/backup/create`, `WikiRoutes.adminBackup`). It needs `config-manage` and a fresh sign-in when that permission is listed in `ngdpbase.auth.step-up`. The backup is written to the backup folder and then downloaded as one streamed `.tar` holding the document and every file beside it (`BackupManager.backupArchive`); the server keeps its copy. Any stored backup can be downloaded the same way from the list (`GET /admin/backup/download/:filename`). The backup key is never in the `.tar`.
- __On a schedule:__ automatic backups are the scheduled job `backup.auto` (`BackupManager.scheduleAutoBackup`, #1720). They are off by default (`ngdpbase.backup.auto-backup: false`). `ngdpbase.backup.auto-backup-time` is `HH:MM` in the server's time zone; `ngdpbase.backup.auto-backup-days` is `daily`, `monthly` (the 1st), `weekdays` or day names such as `Mon,Wed,Fri` (`autoBackupSchedule`). A backup missed while the server was down runs once when it is back, one still running is not doubled, and a failed run is tried up to three times (again after 1 and 5 minutes). The settings are saved from Admin → Backup (`POST /admin/backup/config`, `config-manage`) into `app-custom-config.json`.
- __Where:__ `ngdpbase.backup.directory`, default `${SLOW_STORAGE}/backups`, through the storage provider `ngdpbase.backup.provider` (`filebackupprovider`, the only one). The folder is made owner-only and each file `0600` where the filesystem allows (`FileBackupProvider.writeBackup`, #1560).
- __The files:__ a backup is one gzipped JSON document, `{timestamp}-ngdpbase-backup.json.gz` (`.json.gz.enc` when encrypted, below), shaped `{ version: "1.0.0", timestamp, application: "ngdpbase", managers: { <ManagerName>: <that manager's backup()> } }` (`BackupManager.createBackup`), plus the files the managers write beside it, which the document references and which are pruned and downloaded with it (`isCompanionOf`):
  - one encrypted file per database, `<stem>.<name>.db` (below);
  - one `.tar` per folder of files ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876)), `.tar.enc` when encrypted: `<stem>.attachments.tar` (the shared attachment pool, without its `.thumbs` thumbnails, which are made again on demand, and without the metadata file the document already holds), `<stem>.vault-attachments.tar` (every vault's `attachments/` folder and `files-index.json`, as stored: a sealed vault's files stay sealed bytes), `<stem>.roles.tar`, `<stem>.persons.tar`, `<stem>.organizations.tar`, `<stem>.footnotes.tar`, `<stem>.comments.tar`, `<stem>.credentials.tar.enc` (the credentials store, only ever encrypted), `<stem>.audit.tar` (the audit log and its archives), `<stem>.jobs.tar` (file-based job state, without the slot locks) and one per add-on that keeps files (`<stem>.forms.tar`, `<stem>.calendar.tar`, `<stem>.feeds.tar`), and `<stem>.env.tar.enc` (the instance `.env`, only ever encrypted; [below](#what-a-backup-holds)). Each is written and read as a stream, file by file, so no file is ever whole in memory, and no file's bytes are in the JSON (`src/utils/treeArchive.ts`). A symbolic link or other non-file in one of these folders is left out and named in the backup's warnings.
- __Encryption__ ([#1561](https://github.com/jwilleke/ngdpbase/issues/1561), #1876 slice 2). With `NGDPBASE_BACKUP_KEY` set (`src/utils/backupKey.ts`, the one declaration, shared with `DatabaseManager`) the document and every `.tar` are encrypted under it by `src/utils/backupCrypto.ts`: AES-256-GCM in 64 KiB records, the key derived per file with scrypt and a random salt, each record's nonce and additional data binding its place, the last-record mark and the file's header, so a changed, reordered, dropped or cut-off record fails. The header carries the key's fingerprint (`backupKeyFingerprint`), never the key: a restore under another key is refused by name before anything is read. The header is not authenticated until the first record verifies, so format 1 has one key-derivation cost: a header asking for another, or a salt or nonce prefix of the wrong size, is refused before any key is derived (a crafted file can't make the server run a huge scrypt). Each part's entry in the document records the fingerprint too, and a part that should be encrypted is never read from a plain file put in its place. The databases are encrypted by SQLCipher under the same key, as before. The document is still built whole in memory, then encrypted.
- __Without the backup key__ nothing is encrypted: the document (password hashes, every user record, the custom configuration with its secrets) and the `.tar` files are written in the clear, as before slice 2, and the credentials store and the databases are left out. That is said twice, never once per backup (operator, [#1912](https://github.com/jwilleke/ngdpbase/pull/1912)): `BackupManager` is marked as needing attention with `BACKUP_KEY_MISSING` for as long as the key is missing (`markNeedsAttention`, [#1948](https://github.com/jwilleke/ngdpbase/pull/1948)) — listed on the `/admin` dashboard under "Working, but needs your attention", checked at start and at each backup, cleared once the key is set — and admins get ONE error notification, "Backups are not encrypted", the first time, naming what is left out. A part left out only for want of the key (its message starts `LEFT_OUT_FOR_NO_KEY`, `src/utils/backupKey.ts`) sends no "A backup is incomplete"; any other failure still does at every backup, naming only the other causes. A restore's safety backup still refuses either. It is deduplicated the way `pageMetadataMissing` dedupes its one-time notice: by its title among the stored notifications, which persist across restarts and keep a dismissed one. Deleting that notification lets it come once more. A site restore then can't be staged, because its complete safety backup can't be taken.
- __Databases:__ `DatabaseManager.backup` copies the application database and every declared add-on database ([#1860](https://github.com/jwilleke/ngdpbase/issues/1860)), on or off, at one point in time, on a worker thread (`src/providers/sqliteBackupWorker.ts`), each encrypted under `NGDPBASE_BACKUP_KEY` (environment or instance `.env` only, never config). Each backup records a `keyFingerprint` of that key, never the key. Without the key no database is written: `DatabaseManager` is degraded (an outage on the `/admin` dashboard), the backup-key notice says so (above), and `DatabaseManager` also notifies admins "Databases are not safely backed up" at each start (`reportAtBoot`). A backup key equal to `NGDPBASE_DATABASE_KEY` still backs up, but lists `DatabaseManager` under "needs your attention", notifies "The backup key is the database key" at each backup, and "Databases are not safely backed up" at each start. `ngdpbase.database.backup.worker-timeout-ms` (default `3600000`) limits the worker's copy, and a restore's staging. With `ngdpbase.database.provider` `none` (the default) there is no database and nothing to copy.
- __One at a time__ ([#1563](https://github.com/jwilleke/ngdpbase/issues/1563)): `BackupManager` runs a backup with its pruning, a restore's safety backup and staging (`restoreFromFile`), and the routine health check (`refreshBackupHealth`, the `backup.health` job) one after another, never side by side (`exclusive`, an in-process queue). A backup asked for while one runs — by hand, by the schedule, or several Admin → Backup requests at once — waits for it, then is taken in its own right: its own document, its own result, its own failure. It does not join the running one. There is no wait limit: the wait is as long as the backup ahead of it, which its own limits bound (the database worker, the read-back). So a backup's pruning never deletes files another backup, a restore or the health check is reading. Admin → Backup's page reads (the list, `getBackupHealth`) are not queued: they never wait behind a backup, and a file pruned between listing the folder and reading its size is left out of the list, not an error (`FileBackupProvider.listBackupObjects`).
- __How it is filled:__ `createBackup` calls `backup()` on every registered manager, core and add-on, in registration order, and writes every folder or file a manager declares (`BaseManager.backupFolders()`) and every loaded add-on's `dataPath` beside the document itself ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985); [rules below](#rules-for-developers-and-add-on-authors)). A manager that throws gets `{ error, timestamp }` in its slot, and a manager can report a part it missed in `warnings`. The backup carries on and is written, and then admins get an error notification "A backup is incomplete" naming each missing part. It is also recorded as a failed backup: Backup shows as not working until a whole backup is taken, and an incomplete backup is not the last good one (below). It is still not a snapshot (#1213).
- __A page or file deleted during a backup is skipped, not a failure__ (#1563). The site keeps running while it is backed up, so an entry listed at the start of a part can be gone when it is read: a page deleted, with its version folder. That entry — `ENOENT` on something that was listed — is left out and counted, never an incomplete backup: the pages, version files and trash (`FileSystemProvider.skipVanished`; the count is `statistics.vanished` in PageManager's entry and in the log), and every `.tar` part (`writeTreeArchive` writes the archive again from a fresh listing, without the entry, and names it in `vanished`, logged at info). Every other error — `EACCES`, `EIO`, the pages folder itself missing — still fails the part, and the backup is incomplete. A site without a required-pages folder backs up none, as before.
- __Retention:__ after each backup the oldest backups beyond `ngdpbase.backup.max-backups` (default 10) are deleted with every file beside them, encrypted or not, by-hand and automatic alike (`BackupManager.cleanupOldBackups`, `isCompanionOf`), inside that backup's turn in the queue (above). A failed cleanup is only a log warning.
- __Download:__ the `.tar` a download streams holds the document and every file beside it as they are stored, so with the key set it holds only encrypted files; the key is never in it.
- __Record:__ a successful backup writes the `backup-create` audit event, naming who asked and where the file went.
- __Space first__ ([#1563](https://github.com/jwilleke/ngdpbase/issues/1563)): before anything is written, free space at the destination (`BaseBackupProvider.freeSpace`, `statfs` for the file provider) must be at least the last backup's size, document and files beside it, times `ngdpbase.backup.space-margin` (default 1.5); otherwise the backup is refused, "not enough free space … Nothing was written". With no earlier backup, or a provider that can't tell, the check is skipped. A write that fails part-way removes the half-written document.
- __Read back after__ (#1563): the document just written is read back on a worker thread (`verifyBackupOffThread`, `src/utils/backupDocument.ts`) — decrypted under the key (every record's GCM tag), decompressed, parsed and checked — the same `readBackupDocument` a restore uses, limited by `ngdpbase.backup.verify-timeout-ms` (default `600000`). One that does not read back is removed with the files beside it, and the backup fails. The files beside the document are not read back.
- __Failure is loud and persistent__ (#1563, operator: "We need a persistent 'backups not working'"):
  - Any backup that fails — out of space, a write or permission error, a failed encryption, the space check, a failed read-back, or a part missing — marks `BackupManager` degraded as an __outage__ (`markDegraded`, the `/admin` "not working" banner) with the reason and the last good backup's date. It is kept in `ngdpbase.backup.health-file` (default `${FAST_STORAGE}/backup-health.json`) and stays, across restarts, until a backup succeeds. By hand or scheduled alike.
  - Admins get one error notification, "Backups are not working", per reason, not per attempt — several backups asked for at once that fail the same way are one notification, since they run one after another and each reads the reason the one before kept; it goes through `NotificationManager`, so its email escalation applies. A backup with a part missing keeps its own "A backup is incomplete" notice instead, one per backup, and that backup is not counted as the last good one.
  - __Silence is a failure__: no good backup within the window is the same outage, "No good backup since" and the date, or "never" on a site that has none — so a new site shows it until its first backup. The window is `ngdpbase.backup.stale-interval-multiplier` (default 2) times the longest gap between `backup.auto` runs while automatic backups are on and scheduled, and `ngdpbase.backup.stale-fallback-days` (default 7) while they are off, paused, or unscheduled. One notification per stretch, kept across restarts. Checked at start, after every backup, and by the routine job `backup.health` every `ngdpbase.backup.health-check-interval` ms (default one hour, as the system principal).
  - The last good backup is read from the backup directory each time (the newest document there, other than one a kept failure names), never remembered.
  - The outage replaces the backup key's reminders on the dashboard; they come back once backups work.
  - A scheduled backup that fails also posts the job's own error notification ("Automatic backup failed") on each failed attempt, and the job records `job-failed` after the last (`BackgroundJobManager`). A success posts an "Automatic backup complete" notification.
  - Automatic backups switched on with a time or days setting that can't be read: an admin error notification ("Automatic backups are not running") and an error log line; nothing runs until it is fixed, and the no-recent-backup window is the fallback one.
  - A backup folder that can't be used at start (for example an unmounted volume): `BackupManager` is marked degraded, which the `/admin` dashboard shows, and backups are off until restart (`BaseManager.preflightConfiguredPath`).
- __Shown__ (#1563): Admin → Backup and the `/admin` dashboard show the last successful backup (time in the viewer's local zone, size, location), the next automatic backup, and free space at the destination (`BackupManager.getBackupHealth`, `views/_backup-health.ejs`).
- `ngdpbase.backup.compress` and `ngdpbase.backup.auto-backup-interval` are in the default config but nothing reads them. Compression is always on and the schedule is the time and days settings.

## What a backup holds

"Yes" means the data is in the backup: the `.json.gz`, or for databases the encrypted files beside it. "No" means the backup has nothing of it, so a copy of the folder is the only backup there is. Rows marked "probe" were confirmed in a backup taken on a throwaway instance.

| --- | --- | --- | --- |
| Pages, current text (public and required pages) | Yes (probe) | PageManager | `FileSystemProvider.backup`: every `.md` under the pages and required-pages folders |
| Page version history | Yes, with `versioningfileprovider` (probe). The shipped default `filesystemprovider` keeps no history | PageManager | `VersioningFileProvider.backup` → `readVersionFiles` (read and written as UTF-8 text) |
| Public trash (deleted pages) | Yes, with `versioningfileprovider` (probe) | PageManager | `VersioningFileProvider.readTrash` |
| Page index (`page-index.json`) | No; rebuilt from the version manifests when it is empty at start | PageManager | `VersioningFileProvider.rebuildPageIndexFromManifests` |
| Private stores / vaults | Yes, every file of every vault as stored, sealed files still sealed: pages, history, trash, footnotes and comments, `store.json`, and each user's `user-keys.json` (probe: a vault page, its history and its indexes). Not the vault's files and their `files-index.json`, which are AttachmentManager's (next rows). __None of it__ when the whole private tree is over 256 MB; the backup then carries `privateOmitted` and the server logs an error | PageManager | `FileSystemProvider.backupPrivateStores`, `privateStoreTakeout.collectUser` (`skip`) |

| Sign-in sessions (`sessions/`) | No; people sign in again | none | |
| Configuration: `app-custom-config.json` | Yes, as written, secrets included (probe). Copies of the default and merged configuration are carried for reference; only the custom file would be restored | ConfigurationManager | `ConfigurationManager.backup` |
| `<FAST_STORAGE>/.env` and the keys in it | Yes, as `<stem>.env.tar.enc`, only ever encrypted, __without the `NGDPBASE_BACKUP_KEY` line__ (a backup never holds the key to itself). | Audit log | Yes, with `fileauditprovider`: the live log and every archive as `<stem>.audit.tar`, the queue flushed first; only the audit files, never the application logs in the same folder. | Search index | Yes, the shared Lunr documents; private page text is left out (probe). Elasticsearch: at most the first 10,000 documents. Either can be rebuilt from the pages | SearchManager | `LunrSearchProvider.backup`, `ElasticsearchSearchProvider.backup` (`size: 10000`) |

| User keywords vocabulary | Yes | CatalogManager | `CatalogManager.backup` |

| OpenID Connect provider | Client registrations are configuration (`oidc-auth-server.clients`), so they travel with it. Live grants: a list for incident response, can't be restored. Signing and cookie keys: no (`.env`) | OidcManager | `OidcManager.backup`, `restore` throws |
| Scheduled-job state | With a database (`ngdpbase.jobs.state.provider: auto` and the database open) it is tables in the application database, so in the database copy. In files (`ngdpbase.jobs.state.dir`): yes, as `<stem>.jobs.tar` — state, run history and checkpoints, without the slot locks (#1876 slice 2; tests) | BackgroundJobManager | a declared folder while job state is in files (`BackgroundJobManager.backupFolders`), written by BackupManager |
| Shares, notifications | No, by decision: a restore leaves them as they are and names them in its notification | ShareManager, NotificationManager | no `backup()` |
| Add-ons on or off | A list only; restore does nothing | AddonsManager | `AddonsManager.backup` |

## Restore today

Admin → Backup has two restores, both of a backup stored on the server, both staged for the next start:

- __Restore the whole site__ ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945)), the main card, on every site: the staged site restore of [#1876](https://github.com/jwilleke/ngdpbase/issues/1876) (below). Pages, users, settings and every other manager without a staged restore are left as they are.
- __Restore the databases only__ ([#1723](https://github.com/jwilleke/ngdpbase/issues/1723), merged as 26a11b58), the second option, only on a site that keeps databases. Keeping it beside the whole-site restore is the operator's first-cut choice for #1945 and can be reversed.

The "Restore Data" button and `POST /api/admin/restore` that older documents describe were never built.

### Restoring the whole site

As built for [#1945](https://github.com/jwilleke/ngdpbase/issues/1945), with the same permission, confirmation, record and safety backup as the databases restore below:

- __Where:__ Admin → Backup → __Restore the whole site__, shown on every site, with or without databases. The form posts `scope=site` to `POST /admin/backup/restore` (`WikiRoutes.adminBackupRestore`), which needs `config-manage`, with its fresh sign-in when listed in `ngdpbase.auth.step-up`. The route only checks the typed name and calls `BackupManager.startRestore(ctx, filename, { scope: 'site', replace })`; the manager decides the rest (Manager-SOT).
- __What the card says__, before the confirmation: what it puts back and what it does not, in the words of the "not restored" notification (`BackupManager.siteRestoreScope()`: `restoreLabel` of every manager on this site whose restore is staged; of every labelled manager without one; then `NEVER_IN_A_BACKUP`), so the card and the notification after the restart never disagree. Also: the instance `.env` comes back only from an encrypted backup; an encrypted backup needs the same backup key on this server; a fresh backup is taken first; nothing changes until the site is restarted, and the site never restarts by itself. The no-backup-key notice ([below](#a-site-with-no-backup-key)) is on this card.
- __Which backup:__ any backup in the backup folder, picked from a list; one taken without the backup key is marked "not encrypted: no sign-in credentials, no keys". There is no upload.
- __Confirm:__ type the site name; the server checks it again.
- __What happens:__ `startRestore` records `backup-restore` (or `backup-restore-replace`) with `scope: 'site'` and the backup's parts before anything else, and refuses to start if that can't be recorded. In the background it then calls `restoreFromFile` with a `managerFilter` naming exactly the managers on this site whose restore is staged, so a manager without one is never restored live from the page: the site restore below runs, takes its safety backup, stages every part and the `.env`, and notifies "A site restore is staged". If it fails, admins get "Restore of … was not staged" with the reason, and the site's data stays as it is.
- __Never replaced silently:__ a staged restore of either kind, site or databases-only, refuses a new one; __Replace it__ (same typed confirmation) replaces it and is recorded as `backup-restore-replace`. A staged site restore is shown on the card (backup, when taken, staged when and by whom, the safety backup) with __Cancel staged restore__. `POST /admin/backup/restore/cancel` calls `BackupManager.cancelStagedRestore(ctx)`, which cancels whichever is staged and records `backup-restore-cancel`. While a site restore is staged, the databases-only form is not offered: the site restore includes the databases.
- __Audit:__ the existing `backup-restore`, `backup-restore-replace` and `backup-restore-cancel` entries are reused; `metadata.scope` says which restore. Their catalog descriptions still say "databases".

### Restoring the databases

The operator's decisions D1 to D6 are in the [decision log](https://github.com/jwilleke/ngdpbase/issues/1723#issuecomment-6248360904). As shipped:

- __Where:__ Admin → Backup → __Restore the databases only__ (`POST /admin/backup/restore` without `scope`, `WikiRoutes.adminBackupRestore`), the second option below the whole-site restore, shown when databases are enabled or when the application database can't be opened. It needs `config-manage`, with its fresh sign-in when listed in `ngdpbase.auth.step-up`. The card says "Restores the databases only. Pages, users and settings are not changed." (D6).
- __Which backup:__ one already in the backup folder, picked from a list (D1, `BackupManager.findStoredBackup`). There is no upload. A backup that holds no database can't be picked.
- __Confirm:__ type the site name (`ngdpbase.application-name`). The server checks it again and restores nothing when it doesn't match.
- __What happens:__ `BackupManager.startRestore` records `backup-restore` before anything else, and refuses to start if that can't be recorded. In the background it then:
  - 1 takes a complete safety backup of the live data, or stops if any part of it is missing (`restoreFromFile`, `requireComplete`). When the application database can't be opened ([#1892](https://github.com/jwilleke/ngdpbase/issues/1892) D2), the safety backup leaves the databases out and records that (`leftOut` in DatabaseManager's entry, with a note); everything else must still be there. The restore then needs `NGDPBASE_DATABASE_KEY` set, and the card and the "staged" notification say what the safety backup left out;
  - 2 has `DatabaseManager.restore` check the backup key's fingerprint, refusing a backup made with another key;
  - 3 stages each database as `<live>.staged` under the site's database key, all or nothing, with a manifest.
- __Undeclared databases:__ a backed-up add-on database this site doesn't declare is skipped, and admins are told (D4).
- __Notifications:__ admins are notified when the restore is staged, naming the safety backup, or why it wasn't. If it fails, the databases in use are not changed.
- __At the next start:__ before any database opens, each live file and its `-wal`/`-shm` are moved aside as `*.pre-restore` (a damaged file that couldn't be opened included: the failed open wrote nothing to it or its WAL) and the staged file takes its place (`sqliteBackup.applyStagedRestore`). A partial set, an orphan staged file, or a manifest naming a path it shouldn't is set aside as `*.incomplete`, and admins are told. A rename that fails while applying opens no database: the site starts in maintenance mode and admins get "Critical: the application database is not available", with the files left as they were at the failure ([#1892](https://github.com/jwilleke/ngdpbase/issues/1892)). So does a restored file that then doesn't open. The site never restarts itself; the admin restarts it.
- __A staged restore is shown__ on the card: which backup, when it was taken, when staged, by whom, and the safety backup (restoring that undoes this restore). __Cancel staged restore__ (`POST /admin/backup/restore/cancel`) is recorded as `backup-restore-cancel`. __Replace it__ uses the same typed confirmation and is recorded as `backup-restore-replace`. A second restore without replacing is refused (D5).
- __Key:__ the backup needs the `NGDPBASE_BACKUP_KEY` it was made with (D3). An encrypted document is read only under it; a backup taken before slice 2, with a plain document, still restores.
- __After the restart__ the critical "not restored" notification lists everything but the databases (below).

### The staged site restore (#1876)

`BackupManager.restoreFromFile(ctx, path)` with no `managerFilter` (or one naming any staged part besides the databases) stages a __site restore__. Every part whose restore is staged goes in: the declared folders and files of `RoleManager`, `PersonManager`, `OrganizationManager`, `FootnoteManager`, `CommentManager`, `AuthManager` and `BackgroundJobManager`, and every loaded add-on's (its `dataPath` and declared folders), which BackupManager stages itself ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)); and the parts of the managers that stage their own (`restoreIsStaged()`: `DatabaseManager`, `AttachmentManager`, `AuditManager`). One record binds the parts together: the site restore manifest, `ngdpbase.backup.restore-manifest` (default `${FAST_STORAGE}/site-restore.json`; `src/utils/siteRestore.ts`).

- __Refused first__ when a site restore or a database restore is already staged (unless `replaceStaged`), or when the backup's entry for any staged part is an error. A databases-only restore (`startRestore` with the default scope) is refused while a site restore is staged, since it includes the databases.
- __Then a complete backup of the live data__ (`requireComplete`, `safetyBackup`), as for the databases. It now holds every part above, so restoring it undoes the restore.
- __Then staging, all or nothing.__ The manifest is written in state `staging`; each part stages beside its live data and records the pairs it will swap: the databases as `<file>.staged` (#1723), each folder as `<folder>.staged` (extracted from its `.tar`), the shared pool as `<pool>.staged` with the metadata file written from the document, each vault's `attachments.staged` and `files-index.json.staged`, the credentials store as `credentials.json.staged` (an empty store when the backup's was absent), and the audit files as the folder `audit.log.staged/` (refused when the archive holds anything but audit files). A part the backup left out — the credentials store of a backup taken without the key, job state files when this site keeps job state in the database — stages nothing and is named as not restored. Every encrypted part is read only under the key its fingerprint names. A part that fails discards every part already staged, the databases included, and the manifest; the live data is never touched. The manifest is set to `staged` only when every part is: that is the commit. Admins are notified "A site restore is staged", naming the safety backup.
- __A sealed vault never takes plaintext__ (#1836): a vault that must be sealed on this site whose files in the backup are not all sealed bytes refuses the whole staging. A vault the backup has and this site no longer has is not staged, and admins are told.
- __Paths in a backup are data.__ An archive name in the document must be a bare file name in the backup directory; an archive entry that is absolute, climbs out (`..`) or is not a file or folder (a symbolic link) refuses the extract.
- __Nothing is restored live while a site restore is staged.__ The managers in the backup without a staged restore (pages, users, settings, the search index, …) are left out of the site restore — listed in `results.skipped`, never written into the running site — and named in the notification. A later `restoreFromFile` that would restore any of them live is refused until the staged restore is cancelled or applied.
- __At the next start__, each part is applied before its owner reads it: `DatabaseManager` first, before any database opens; a manager's declared parts in `BaseManager.initialize()`, before the subclass reads them (BackupManager's `applyStagedPartsAtStart`, which needs only the configuration, so it works for managers that start before BackupManager); an add-on's as AddonsManager loads it, just before its `register()` ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). A part goes in only when the manifest is committed and every part still pending has all its staged files: then each live path steps aside as `<live>.pre-restore` and the staged one takes its name, a rename, and the part is marked applied in the manifest. Otherwise every part is set aside as `*.incomplete` and nothing of it is applied, the databases included. An owner refuses a manifest naming a path that isn't its own. Staged files with no manifest naming them (an interrupted staging) are set aside. A manifest that can't be read applies nothing and is left as it is, and the parts' managers show degraded.
- __Admins are told__ once every manager and add-on has started (`BackupManager.reportRestoreAtBoot`, called at the end of `WikiEngine.initializeAddons`): "A site restore was applied", "… was not applied" (with why) or "… was applied only in part" (a rename that failed while applying, or a part whose manager didn't start, such as an add-on now turned off). The record is kept as `<manifest>.last`. After any restore that was applied, site or databases-only, the critical notification below follows.
- `getStagedSiteRestore()` returns the staged manifest; `cancelStagedSiteRestore(ctx)` records `backup-restore-cancel` (refuse) and removes every staged file and the manifest. Admin → Backup shows the first and reaches the second through `cancelStagedRestore(ctx)` ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945)).

### What each staged part does at the restart

- __Instance `.env`__ (BackupManager's part, applied by `bootstrap-env.ts` before the file is loaded, so before every other part): the backup's file takes the live one's place, kept as `.env.pre-restore`. The live `NGDPBASE_BACKUP_KEY` line is kept (it is never in a backup), and so is the live `NGDPBASE_DATABASE_KEY` line: the restored databases were staged under this site's database key, so that is the key they open with. Everything else — the credentials key (which the restored credentials store's rows are signed with), the session secret, OpenID Connect keys, mail and add-on secrets — comes from the backup. The environment is reloaded from it; a variable set in the ambient environment (Kubernetes `env:`) always wins over the file, as at every start.

- __Credentials store__ (`AuthManager`): the backed-up file takes the live one's name before the store is read; the live one is kept as `credentials.json.pre-restore`. Its rows are signed with `NGDPBASE_CREDENTIALS_KEY`: on a site with another credentials key they don't verify, are held in quarantine, and can be re-signed with `scripts/retrust-credentials.ts` (#1633). Passkeys, devices and linked identities added after the backup are gone from the restored store.
- __Audit log__ (`FileAuditProvider`, before it reads the chain head): every audit file now in the folder — the live log and all its archives, newer ones included — moves into `audit.log.pre-restore/`, and the backup's take their names. The application logs in the same folder are not touched. The chain resumes from the backup's last record, so the restored log verifies from where it began up to the backup and on through every new record. The records written after the backup are in `audit.log.pre-restore/` and verify there as they did. A chain-head witness (`ngdpbase.audit.chain-witness.destination`) keeps the heads it published after the backup: they are ahead of the restored log, exactly as a cut-off tail would look, and the pre-restore folder is what answers them. The `backup-restore` record written when the restore was staged is in the pre-restore folder too, not in the restored log.
- __File job state__ (`BackgroundJobManager`, before the state is opened): the runs in the live state started after the backup are read first, then the folder is swapped. The slot locks were never in the backup.
- __Add-on files__: AddonsManager swaps the add-on's `dataPath` and declared folders in just before the add-on's `register()`, so before any of its managers reads them ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)).

### A job run in progress at backup time

Verified in `BackgroundJobManager` and its tests (`BackgroundJobManager.restore.test.ts`). A backup taken while a scheduled run is going holds that run as the job's current run, `running`, with its slot not done. Job state in the database comes back that way with the database; job state in files with the job state part.

- __What a plain restart does with such a run__ (#1716) is resume it: once its lock has run out it counts as a crashed attempt and is retried after its backoff, as attempt 2, with its checkpoint; a run started by hand is restarted for the person who started it; and every slot due since then is caught up by the job's catch-up rule. After a restore that would re-run work that already happened on the site after the backup.
- __So after a restore it does not__ (#1876 slice 2): when the job state was put back at this start (file state applied, or `DatabaseManager.restoredAtStart()` with database job state), each scheduled job's first look closes its current run as `failed` ("cut off by a restore … not run again", recorded as `job-failed`), never resumed or retried, and its next slot is the next one from now, so nothing between the backup and the restore is caught up. A run started by hand that was unfinished is reported cut off and not restarted. __Jobs are never re-run because of a restore__; the notification below names what ran in between so an admin can decide.

### Not restored

What a restore does not bring back, so it is known before a restore, not only after. After any restore applies (site or databases-only), `BackupManager` sends admins a __critical__ notification, "Critical: a restore did not bring everything back" (error level), with:

- __What was put back__: the parts applied.
- __Not restored__, still as they were before the restore:
  - in no backup at all (`NEVER_IN_A_BACKUP`): shares (share links stay as they are — operator decision, 2026-10-20), notifications, sign-in sessions, the backup key itself and the database key (they stay as they are on this site), TLS certificate files, the media library and its index;
  - every part of the backup with data that was not staged: for a site restore the managers without a staged restore — pages (with history, trash and private stores), user accounts, settings, the search index, the user-keywords vocabulary, the add-on list, agent tokens, OpenID Connect grants — and a part the backup left out (the credentials store of a backup taken without the key); for a databases-only restore everything but the databases;
  - a part that was set aside at the start.
- __Job runs between the backup and the restore__: per job, its name, when it last ran and how that ended (and how many runs there were), read from the live job state __as it was when it was replaced__ — when the restore was staged (`BackgroundJobManager.runsSince`), and again at the start: file job state just before the swap, database job state from the application database DatabaseManager kept as `*.pre-restore` at the swap (`DatabaseManager.readReplacedApplicationDatabase`, read-only, nothing migrated), so runs between staging and the restart are named too. Those runs are not in the restored history, and they are not run again.

At the same start, `BackupManager` records `backup-restore-applied` (operator-approved catalog entry, on-failure continue) into the restored audit log: which backup, when it was taken, who started the restore, site or databases-only, and the parts applied. So the restored log itself says a restore happened; the `backup-restore` record of the staging is in the log it replaced (`audit.log.pre-restore/`).

The record behind it is BackupManager's own file beside the manifest, `<manifest>.report.json`, written when the restore is staged and removed once read (or when the restore is cancelled).

### Everything else

Pages (with history, trash and vaults), users, settings, the search index, the user-keywords vocabulary and the add-on list have no staged restore. A site restore leaves them out and names them (above); restoring them __live__ with `restoreFromFile` and a `managerFilter` still writes into the running site, and is refused while a site restore is staged. Nothing calls it that way today: Admin → Backup's whole-site restore names only the managers whose restore is staged. `AgentTokenManager` and `OidcManager` refuse by design. [#1876](https://github.com/jwilleke/ngdpbase/issues/1876) is closed without a staged restore for these; no open issue tracks it.

## What to keep safe

The operator plan "one thing to save" ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876#issuecomment-6286342587), 2026-10-20):

- __The operator keeps the backup key.__ Every site has one (`NGDPBASE_BACKUP_KEY`, made at first start). Every backup is encrypted under it, and it is the one thing a restore on a new server needs: set the one saved key, restore, and everything in the backup returns — the `.env` keys, the credentials store with every admin's passkeys, the databases. Admin → Backup shows its fingerprint; __Show the key to copy it__ (`GET /admin/backup/key`, `config-manage` with its fresh sign-in, never cached; the only place the key is ever shown) and __I have saved this key off the server__ (`POST /admin/backup/key/saved`) records the fingerprint in `ngdpbase.backup.key-saved-fingerprint`. Until then the dashboard banner says "Save the backup key off this server" with the fingerprint; a new key asks again. On a new server put the saved key in `<FAST_STORAGE>/.env` before the first start (or replace the one that server made, then restart).
- __The operator may also keep the whole `.env`__ ([#1938](https://github.com/jwilleke/ngdpbase/issues/1938), operator decision 2026-10-21: the browser downloads it and the operator chooses where it is kept; no server-side copy). __Download .env__ in the backup-key card (`GET /admin/backup/env`, `WikiRoutes.adminBackupEnv`) sends `<FAST_STORAGE>/.env` exactly as it is on disk, the backup key line included, as an attachment named `<application-name>.env`. It needs `config-manage` with its fresh sign-in, as the key page does (a stale sign-in goes to the prompt and comes back to the download), is sent `Cache-Control: no-store`, and is recorded by `BackupManager.revealInstanceEnv` as `secret-reveal` (`resource: .env`, `resourceType: instance-env`, who and the byte count, never the contents); the contents are never logged. The card says beside the button that the file holds every secret of the site in plain text.
- __A changed `.env` key set asks for a new copy__ ([#1976](https://github.com/jwilleke/ngdpbase/issues/1976)). `BackupManager.checkBackupKey` (at start, after every backup, on each `backup.health` run) reads the names `<FAST_STORAGE>/.env` sets (`envKeyNames`, `dotenv.parse` as `bootstrap-env.ts` reads it, so the keys the boot generated with `ensureInstanceEnvSecret` count as much as a hand edit) and compares them with `ngdpbase.backup.env-keys-saved`, the sorted names recorded when an admin last confirmed. Names only: a value is never kept, logged or shown. The names are stored, not only their fingerprint, so the reminder can say which keys were added or removed. A difference lists Backup under "Working, but needs your attention" (`markNeedsAttention`, "The keys in .env changed since an admin last saved it (added: …; removed: …)") and sends one warning notification, "Save a copy of .env", per difference, deduplicated by its title and words among the stored notifications. The Admin → Backup card names the keys beside __Download .env__ and offers __I have saved .env off the server__ (`POST /admin/backup/key/saved` with `envFingerprint`, the same route and confirmation as the backup key's), which records the names and, when the file holds the site's backup key, the key's fingerprint too: one press clears both reminders. One status slot: an outage, then the missing key, then "Save the backup key …", then the `.env` reminder. __First check:__ with nothing recorded (a new site, or one upgraded to this release), the names found are recorded as the baseline under the system context, without asking (a site not installed yet, with no custom configuration file, is left until the first check after the install): an upgraded site's `.env` is already in every encrypted backup and a new site is already asked to save its backup key. Every change after that asks.
- __Each person keeps their recovery words__ (#1452). A private vault opens only with its owner's password or passkey; a forgotten password and no recovery words means the vault is gone, and no backup or administrator can open it. Each person with vault keys gets one notification, addressed to them, "Keep your recovery words safe", at their first password sign-in after this change (`src/utils/recoveryWordsReminder.ts`); dismissing it is their confirmation, and it is not sent again (deduplicated by title and person among the stored notifications).

### Not in any backup

- __TLS certificate files__: reissue them on the new server.
- __Media library source folders__: the operator's own files, read-only to the site; back them up at the storage level. The media index is rebuilt by a rescan.
- __Sign-in sessions, shares, notifications__: see Not restored.
- __The backup key itself__: a backup never holds the key to itself; that is what the operator saves.

### A site with no backup key

Now only a site whose key was removed and not yet regenerated by a restart (or a backup taken before #1876 slice 2). Admin → Backup says so plainly before any restore: the backup list marks every backup taken without the key "no sign-in credentials"; the whole-site restore card says passwords return to the backup date, passkeys and authenticator apps are not restored, and on a new server admins sign in with a password only and won't have admin rights until they set up a passkey again; the typed confirmation stays.

## What an operator must do today

Only what the code supports:

- __Copy the data folders while the server is stopped.__ Stop with `./server.sh stop`, copy all of `FAST_STORAGE` and `SLOW_STORAGE`, then start again. That copy is the only complete backup: it holds every "No" row above. Stopped matters: the database (SQLite, WAL) and the JSON stores are not safe to copy while they are being written.
- __Save the backup key off the server__ (above). The rest of `<FAST_STORAGE>/.env` is in every backup now; the backup key is what opens it. Keep `NGDPBASE_DATABASE_KEY` too where you can: a copy of the data folder (below) needs it, though a restore does not (it stages the databases under the site's own key). Vaults are sealed with each owner's own key in `user-keys.json`, which opens with their password or recovery words, so a copy restores to the password they had when it was taken.
- __Treat a backup as a partial copy.__ Turn on automatic backups: Admin → Backup can restore the whole site from them, everything but pages, users and settings (and what no backup holds). Without the backup key the document and the `.tar` files beside it hold password hashes, secrets, attachments and records unencrypted, so keep them as safe as the data folder.
- __Restoring pages, users or settings means putting the copy back.__ Stop the server, put the copied folders back where they were, with the same `.env` (__Download .env__ on Admin → Backup keeps a copy of it off the server, #1938), then start.
- __Media__ is never part of the site's data: back up the library at the storage level.

## Rules for developers and add-on authors

- __A manager that keeps data owns its backup.__ Override `backup()` and `restore()` from `BaseManager`. The default `backup()` returns `data: null`, so a manager that keeps state and doesn't override it is silently left out. Say what is missing as the row in this guide.
- __A registered manager without `backup()` has no part, and is not a failure__ ([#1943](https://github.com/jwilleke/ngdpbase/issues/1943)). `BackupManager` calls `backup()` on everything `getRegisteredManagers()` returns that has one; one without it is logged at debug and left out of the document, never an error slot or an "incomplete" backup. A `backup()` that throws is still a failure. A backup taken before the fix holds an error slot for it (`manager.backup is not a function`); a restore skips that slot, and the "not restored" notice names it.
- __Rows in a database: declare it, don't back it up yourself.__ An add-on that keeps rows declares `ngdpbase.addons.<slug>.database` and opens it with `openAddonDatabase` ([#1860](https://github.com/jwilleke/ngdpbase/issues/1860), [storage guide](storage-developer-guide.md#declaring-a-database)). `DatabaseManager` then backs it up and restores it, on or off ([#1723](https://github.com/jwilleke/ngdpbase/issues/1723)); the add-on writes no backup code. Don't write your own copy of a database file.
- __Never write a database backup unencrypted.__ `DatabaseManager` writes database backups only under `NGDPBASE_BACKUP_KEY`, and nothing without it (#1723).
- __Declare your folders; don't write backup code__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). A manager whose data is a folder of files, or one file, declares it in `backupFolders()` (`{ part, folder }`, or `{ part, file, what, whenAbsent }`), resolved from the configuration, and writes no `backup()`, `restore()` or staging code for it. BackupManager writes it as `<stem>.<part>.tar` beside the document, stages it in a site restore, and puts it in place at the next start in `BaseManager.initialize()` — so call `super.initialize()` before you first read the folder. Only BackupManager imports `src/utils/directoryBackup.ts` (`npm run lint:backup`). A manager may also keep data in the document through `backup()`; a declared part's record then goes beside that data as `data[<part>]` (the credentials store beside AuthManager's provider list). Details: [BaseManager](../managers/BaseManager.md#declaring-your-data-folders).
- __An add-on's `dataPath` is backed up for it__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). Every loaded add-on's `dataPath` — `ngdpbase.addons.<slug>.dataPath`, or `<FAST_STORAGE>/<slug>` when that is not set — is backed up as `<stem>.<slug>.tar` when the folder exists, and restored before the add-on's `register()` at the next start. Keep the add-on's files there; a further folder is declared on the module, `backupFolders(config)`. The add-on writes no backup code and imports nothing for it (external add-ons cannot reach core's `dist/`). A `dataPath` that is the instance data folder, or holds it, is refused as one (a restore would swap the whole site's data).
- __Files are encrypted when the key is set__ (#1561). A declared part is, by BackupManager. A manager whose files are not one declared folder (the attachment pool and vaults, the audit log among the application logs) takes each archive's name and key from `options.archive(part)` in its `backup()`, records its `keyFingerprint`, and reads it back through `options.readArchive(manager, archive, keyFingerprint)` in its `restore()`. A secret that must never be in a backup in the clear is declared with `requireKey: true`: without the key it is left out with a warning, as the credentials store is.
- __A part you couldn't back up goes in `warnings`.__ `BackupData.warnings` is turned into the "A backup is incomplete" admin notification (`DatabaseManager.backup` names each database that failed).
- __A backup never carries anything that could be presented.__ Token hashes, session ids and grant secrets stay out, and `restore()` refuses instead of bringing back half a credential. `AgentTokenManager` and `OidcManager` are the pattern (#1111).
- __Private text stays sealed.__ Vault files go into a backup as stored bytes, never decrypted. A restore never writes plaintext into a sealed vault (`FileSystemProvider.restore`, #1836). Search backups leave private page text out (#1458).
- __Paths in a backup are data.__ A `restore()` resolves every relative path and refuses one that leaves its folder, as `FileSystemProvider` and `VersioningFileProvider` do.
- __Backups are never silent__ (#1563). A part that can't be backed up says so: in the backup itself (like `privateOmitted`), in the log at error level, and to admins. BackupManager alone decides whether backups work (`refreshBackupHealth`); a route or view only shows `getBackupHealth()`. A failure in a manager's `backup()` makes the whole backup a failed one, an outage until a backup is whole. Don't swallow an error to keep a backup "complete".
- __Files go beside the document, never in it__ (#1876). Declared folders are; a manager with files of another shape writes them as `<stem>.<part>.tar` through `options.archive(part)` (`writeTreeArchive`), streamed and as stored, and names the archive in its entry. No file's bytes, base64 or otherwise, go in the JSON.
- __A restore is staged__ (#1723 D1, #1876). New restore code stages for the next start, all or nothing, after a fresh backup of the live data, as `DatabaseManager.restore` does. It never writes into the running site. Declared folders and files are staged and applied by BackupManager ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). A manager whose data has another shape returns true from `restoreIsStaged()`, stages beside its live data in `restore(data, { siteRestore })` and records its part (`recordStagedPart`), and applies it at the top of `initialize()` (`applyPartAtStart`) with an `allowed` check naming only its own paths, as DatabaseManager, AttachmentManager and the audit log do. A manager does one or the other, not both.
- __An add-on writes no backup code__ ([#1943](https://github.com/jwilleke/ngdpbase/issues/1943), [#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). Its data is backed up through its declared add-on databases and its `dataPath` (and any folder its module declares), all done by core. Its part is applied as the add-on loads, which is why the restore is reported only after the add-ons have started. An add-on manager does not implement `backup()`/`restore()` and must not add no-op ones.
- __A restore never re-runs a job__ (#1876). State put back from a backup is settled at the first look, never resumed (above). A manager whose state is restored says what changed between the backup and the restore; it does not repeat it.

## Known gaps

- __Without the backup key a backup file is a secret: treat it like one__ ([#1561](https://github.com/jwilleke/ngdpbase/issues/1561)). A `.json.gz` written without `NGDPBASE_BACKUP_KEY` is not encrypted. It carries the custom configuration with its secrets in plain text (the probe's backup held the SMTP password as written), every user record with its password hash, and the text of vaults that aren't sealed. Keep it as safe as the data folder and `.env`: never on a share others can read, and never sent where you wouldn't send the keys. Backups taken before slice 2 are such files whatever the key.
- __A whole-site restore leaves pages, users and settings as they are__ ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876)). They have no staged restore — their `restore()` methods have never run on a real site, and they write live — so a site restore leaves them out, the card on Admin → Backup lists them as not put back, and the notification after the restart names them. Restoring them must be staged as the parts above are; #1876 is closed and no open issue tracks this.
- __A backup with databases can't be restored as a whole site on a site without them__ ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945); read from the code, not run). `DatabaseManager.restore` refuses a backup holding databases when this site has none open, and the site restore is all or nothing, so nothing is staged. Set `ngdpbase.database.provider` to `sqlite` first.
- __The audit catalog still describes `backup-restore`, `backup-restore-replace` and `backup-restore-cancel` as databases restores__ ([#1945](https://github.com/jwilleke/ngdpbase/issues/1945)). The whole-site restore records the first two with `metadata.scope: 'site'`, and a cancelled site restore records `backup-restore-cancel` with its parts; changing the descriptions in `config/app-default-config.json` waits for the operator.
- __Encrypting a backup is in memory for the document__ (#1561). The document is gzipped and encrypted whole in memory, as it was built; every file part is streamed.
- __A plain document is still accepted on a site with the key__, so a backup taken before slice 2 restores; its parts are then read as the plain archives it names. Once a backup records a key fingerprint, its parts are never read from plain files.
- __The start-up record after a restore may read as an unclean shutdown__ (#1876): the restored audit log's last lifecycle record is the start before the backup. The `backup-restore-applied` record that follows it says why.
- __A site restore needs the backup key__ (#1876). Without it the safety backup is incomplete (no credentials store, no `.env`), so staging is refused. Every site gets a key at first start, so this is a site whose key was removed.
- __Shares and notifications are left as they are__ (#1876, operator decision): not in the backup, not cleared by a restore, named in the notification. A share of a page or vault that the restore took back to an older state still points at it.
- __The recovery-words reminder comes at a password sign-in__ (#1876): a person who only ever signs in with a passkey gets it the first time they sign in with their password (which is also when their vaults unlock).
- __A restored `.env` under ambient variables__ (#1876): a key set in the environment (a Kubernetes Secret) wins over the restored file, as at every start; update the Secret yourself if it should change.
- __A site restore's parts are not one point in time__ (#1876, #1213). Each folder is archived in turn while the site keeps writing, after or before the databases' snapshot, so a role change made during a backup may be in one part and not another. A page or file deleted during the backup is no longer a failed backup (#1563): it is skipped and counted, so the backup holds the site as it was after the delete for that entry.
- __A vault the site no longer has is not restored__ (#1876). Its files in the backup are not staged, and admins are told; its pages have no staged restore either.
- __Vaults on the site that the backup doesn't have keep their files__ (#1876). A site restore swaps only the vaults the backup holds.
- __An add-on other than forms, calendar and feeds is recorded as `addon:<slug>`__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). A v5.25.0 site restoring a backup made now does not know that entry: it restores everything else and names the add-on's files as not restored. The bundled three keep their old entry names, so they restore either way.
- __A declared part's name is its archive's name__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). Two owners declaring the same part (an add-on named like a core part: `roles`, `credentials`, `env`, `audit`, `attachments`, `jobs`, …) can't both write `<stem>.<part>.tar`: the second fails, and the backup is reported incomplete.
- __An add-on's `dataPath` that does not exist at backup time is not in the backup__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)): that add-on keeps no files. A restore then leaves the folder the add-on later made as it is.
- __A manager's document data is not restored by a site restore when it also declares folders__ ([#1985](https://github.com/jwilleke/ngdpbase/issues/1985)). Its declared parts are staged; its `restore()` is not called. No manager has both today except AuthManager, whose provider list was never restored.
- __A backup's completeness is not checked__ (#1876). The inventory above is the first pass; every "No" row is missing from the backup.
- __Key rotation__: an old backup's databases need the backup key they were made with; a restore under another key is refused ([#1723](https://github.com/jwilleke/ngdpbase/issues/1723) D3).
- __No command-line restore for a site that won't start__ (deferred, #1723 D1).
- __A restore while the application database is unavailable can't be undone from Admin → Backup__ ([#1892](https://github.com/jwilleke/ngdpbase/issues/1892) D2). Its safety backup holds no database; undoing it means putting the `*.pre-restore` files back by hand, with the server stopped. Meanwhile an ordinary backup from Admin → Backup is reported incomplete, and recorded as a failed backup, and automatic backups don't run.
- __A backup is not a snapshot__ ([#1213](https://github.com/jwilleke/ngdpbase/issues/1213)). The databases are copied at one point in time, but the managers are asked one after another while the site keeps writing. A manager that fails leaves an error in its slot. The backup is still written, admins are told it is incomplete, and it is recorded as a failed backup (Backup shows as not working until a whole one is taken). Narrowed by #1563: an entry deleted while it was being backed up is skipped and counted, not a failure; a file changed while it is read can still be caught half-written in a part, and an edit made during the backup may be in one part and not another.
- __One backup at a time is in-process only__ (#1563). The queue is in one server process; two processes pointed at the same backup directory (which no supported deployment does) would still race each other's pruning. Admin → Backup's page reads are not queued, so a download that starts just before an old backup is pruned can find its files gone; the backup just made is never the one pruned.
- __A vault's own folders still read "can't open" as "empty"__ (#1563): the vault listings that decide which owners and vaults exist (`listPrivateOwners`, `listStoreIds`, `collectUser` in `privateStoreTakeout.ts`) treat any error as no vault. Reading a vault's files no longer hides `EACCES` or `EIO`; only a file or folder that is gone is skipped.
- __Only the document is read back__ ([#1563](https://github.com/jwilleke/ngdpbase/issues/1563)). The files beside it (databases, `.tar` archives) are written by their managers and are not read back after writing.
- __The free-space check is an estimate__ (#1563): the last backup's size times the margin. A first backup has nothing to compare with, and a site that grew a lot since can still run out mid-write; that write then fails and is reported.
- __"No good backup since" uses the server's local time__ (#1563): the banner is one line of text written by the server. The dates on Admin → Backup and the dashboard's backup lines are in the viewer's zone.
- __Private stores over 256 MB are left out whole__ ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876#issuecomment-6248952238); #1387 closed). The backup is built in memory. Over that size `privateOmitted` is set and an error logged, but no admin is notified, and every vault is missing from the backup.
- __Elasticsearch search backups stop at 10,000 documents__ ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876#issuecomment-6248952238)). It can be rebuilt from the pages.
- __A leftover legacy `pages/private/` folder is not backed up__ ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876#issuecomment-6248952238)).
- __Download .env is only the instance file__ ([#1938](https://github.com/jwilleke/ngdpbase/issues/1938)). A variable set in the environment (a Kubernetes Secret, `PORT=… node`) or in the checkout's root `.env` is not in it; keep those where they are set. A site with no `<FAST_STORAGE>/.env` is told so on Admin → Backup.
- __The `.env` reminder watches only the instance file, and only names__ ([#1976](https://github.com/jwilleke/ngdpbase/issues/1976)). A key set in the environment or the root `.env` is not watched, and a changed value under the same name (a rotated secret) does not ask. A change undone and made again after a confirmation repeats words already notified, so it shows on the dashboard without a second notification; deleting the earlier notification lets it come again. Confirming is recorded only as the configuration change (`config-change`), no event of its own.
- __Showing the backup key is not audited__ (#1876). `GET /admin/backup/key` records nothing of its own; Download .env records `secret-reveal`.
- __Two default-config keys do nothing__: `ngdpbase.backup.compress` and `ngdpbase.backup.auto-backup-interval` ([#1876](https://github.com/jwilleke/ngdpbase/issues/1876#issuecomment-6248952238)).

## Checklist

- [ ] Your manager keeps data: its folders and files are declared (`backupFolders()`), and anything else it keeps is in `backup()` / `restore()`, or its row here says why not
- [ ] Your manager calls `super.initialize()` before it first reads a declared folder
- [ ] Your add-on keeps its files under its `dataPath` (or a folder its module declares), and writes no backup code
- [ ] Files you write beside the document are encrypted under the backup key when it is set, and a secret is left out without it
- [ ] Rows are in a declared database (#1860), not a file you copy yourself
- [ ] No token hash, session id or grant secret in a backup; `restore()` refuses where there is nothing safe to restore
- [ ] Vault bytes are backed up as stored, and a restore never writes plaintext into a sealed vault
- [ ] Every path read from a backup is checked to stay in its folder
- [ ] A part that can't be backed up is recorded in the backup, logged at error level, and reported to admins
- [ ] Any restore you add is staged for the next start, all or nothing, after a fresh backup
- [ ] The inventory table and Known gaps here are updated in the same change
