# Rebuild Pages

__Rebuild Pages__ is the recovery action for pages. It re-reads every page that actually exists on disk and rebuilds everything that lists pages from what it finds:

- __the saved page list__ (`page-index.json`), which the server reads at every start to know which pages exist and where each file is
- __the search index__, from scratch — the stored search cache is cleared first
- __the links between pages__ (Referring Pages)

Because the saved page list is rewritten, the corrections survive a restart.

It is the heavier counterpart of __[Reindex Pages](/view/reindex-pages)__, the same relationship as Reindex Media and Rebuild Media:

- __Reindex Pages__ — fast and routine. Refreshes the page list the server holds in memory and rebuilds search from the stored search cache. It does not rewrite the saved page list, and a deleted page's leftover search entry survives it.
- __Rebuild Pages__ — slower. Rewrites the saved page list and the search index from what is on disk, so pages that no longer exist are dropped and pages in the wrong place are corrected.

## When to Rebuild

Use __Rebuild Pages__ when:

- a page opens as "page not found" although it is there, or stops opening after a restart
- deleted pages still appear in search results, the asset picker, or admin listings
- files were added, moved or removed on disk outside the application
- the stored search cache is suspected to be corrupt

Reindex cannot fix these: it works from the same stored lists that hold the stale entries.

## How to Rebuild

- 1 Go to __Admin → Page Management → Rebuild Pages__
- 2 Confirm the action when prompted
- 3 The server re-reads every page on disk and rebuilds the page list, search and links
- 4 A confirmation message shows the page count, the search document count, and how many page-list entries were corrected or removed

On a large instance (10,000+ pages) this takes longer than Reindex and temporarily raises memory use. User sessions, attachments, and media are not affected.
