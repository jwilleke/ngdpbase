# Page Audience

The __Audience__ setting limits a page to the users listed. Anyone not in the audience can neither __read__ nor __edit__ the page. It is optional — leaving all roles unchecked means global access policies apply.

## Roles

%%table-striped
|| Role || Description ||
| admin | Full system access to all features |
| user-admin | Can manage users — create, edit, deactivate, delete |
| editor | Can create, edit, delete, and rename pages |
| contributor | Can create and edit pages |
| reader | Read-only access to content |
| member | Community member — same read access as reader |
| anonymous | Public access without authentication |
/%

## How It Works

- Add one or more __role names__ or individual __usernames__ to limit the page to those users
- Leave __empty__ to apply the global access policies (the default)
- Audience entries can be __role names__ (e.g. `editor`) or __usernames__ (e.g. `jim`) — both are matched
- A user you add is kept by the id of their account, and shown as their username followed by that id, for example `jim (urn:uuid:3f6c2a9e-…)`. If that account is removed, the entry shows `jim (no account)` and lets nobody in: a new account that later takes the same username is not in the audience
- An entry can also be __`addon:` and an add-on's name__ (e.g. `addon:phr`): the users who turned that add-on on for themselves on their Profile. See __Add-ons each user turns on__ below
- Anyone who matches __one__ entry can view the page
- Anyone who matches __no__ entry can neither view nor edit the page: it is left out of their lists and search results, and they cannot open it in the editor, save it, rename it or delete it
- Being in the audience does __not__ grant edit access by itself. Who may edit is still decided by the access policies, so a reader in the audience can view the page but not edit it
- __Administrators are the exception__: an administrator can view and edit every page, whatever its audience, and sees these pages in lists and search results

## Add-ons each user turns on

Some add-ons are something each user turns on for themselves, on their Profile. A page with the audience `addon:` followed by the add-on's name is for the users who turned that add-on on:

```yaml
audience:
  - addon:phr
```

- Users who turned the add-on on see the page, in lists and in search results
- Everyone else, and visitors who are not signed in, do not — they are told they may not view it, and it is left out of lists and search results
- Administrators can still view and edit the page, as with any audience
- If the name is not an add-on that users turn on for themselves on this site, nobody matches that entry. The page is not opened to everyone, and the site's administrators are warned

## Per-Action Access (`access` field)

For more granular control, use the `access` frontmatter field instead of `audience`. It accepts an object keyed by action name, each with an array of principals:

```yaml
access:
  view:
    - reader
    - editor
  edit:
    - editor
```

`access` is different from `audience` in two ways: each list covers only the action it names, and administrators are __not__ an exception — `access: view: [editor]` keeps out an administrator who is not an editor. A page with both an audience and an `access` list is open only to someone who passes both.

## The `private` Flag

If a page is marked __Private__, it is kept in its owner's own private area and the Audience field is bypassed entirely. Only the __owner__ can read it — the page's author, as recorded when the page was first saved. Nobody else reaches it, administrators included.

> __Ownership__: ownership is the author recorded when the page was first saved, not the `author` field as it stands now. Editing that field later does not change who owns the page.

### Applying the `private` Flag

Check the __Private__ checkbox on the page's Edit form (or on the Create New Page form for new pages), or set it directly in frontmatter:

```yaml
private: true
```

The `private` frontmatter field is the canonical signal. Earlier versions of [{$applicationname}] stored privacy as a `user-keywords: [private]` entry; that mechanism was removed in v3.7.0 and all pages have been migrated.

### Private vs Audience

%%table-striped
|| Feature || Audience field || Private flag ||
| Where configured | `audience:` frontmatter / Edit form | `private:` frontmatter / Private checkbox |
| Who can view | Any roles or usernames listed, and administrators | The owner only |
| Storage location | Normal page store | The owner's own private area |
| Bypasses Audience | — | Yes — Audience setting is ignored |
/%

The Private flag takes precedence. If a page has both an Audience setting and `private: true`, the Audience setting is ignored. See [Page Private] for the full description, precedence rules, and what Private does not do.
