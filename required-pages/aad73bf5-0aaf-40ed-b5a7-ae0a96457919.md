# Backup

[{$pagename}] operations allow administrators to protect platform data against loss.

ngdpbase has __two separate layers of data__ that require different backup strategies.
A complete backup requires both.

## 1. Structured Data Backup ("Backup Data" button)

Found at [Admin → Backup Management|/admin/backup].

The __Create & Download Backup__ button:

1. Calls `backup()` on every registered manager
2. Aggregates results into a single JSON document
3. Compresses with gzip
4. Downloads it as one `.tar` file: the backup document (`<timestamp>-ngdpbase-backup.json.gz.enc`), the files kept beside it (attachments, vault files, role membership, user and contact records, organizations, footnotes and comments, the sign-in credentials, the audit log, scheduled-job state and add-on files, each as its own `.tar.enc`) and, when the site keeps databases, an encrypted copy of each. With the backup key set, every one of these files is encrypted with it
5. Retains the last [{ConfigAccessorPlugin key="ngdpbase.backup.max-backups" valueonly=true}] backups on the server

### What IS included

%%table-striped
|| Data || Notes ||
| Configuration settings | The site's own settings, as written, secrets included |
| User accounts | Usernames, hashed passwords, preferences |
| Role membership | Who holds which role |
| Users, contacts and organizations | The records about each user, contact and organization |
| Page files (`.md`) | Every page, including required pages |
| Page version history and deleted pages | When page history is turned on |
| Private stores (vaults) | Pages, history, footnotes and comments, as stored: sealed files stay sealed. Left out when all vaults together are over 256 MB |
| Attachment files | Every uploaded file, with its details (name, type, which pages use it) |
| Vault files | Files on vault pages, exactly as stored: never decrypted |
| Footnotes and comments | On public pages |
| Sign-in credentials | Passkeys, authenticator apps, verified email and phone, known devices, linked sign-ins and proxy grants. Only when the backup key is set: they are never in a backup unencrypted |
| The keys and secrets in `.env` | Everything except the backup key itself. When restored, the site keeps its own backup key and database key |
| Shared folders' keys | Each shared folder's key, as stored: locked under the shared-folders key and the recovery words, never readable on its own. The shared-folders key itself comes back with `.env` |
| The audit log | With its tamper-evident chain |
| Scheduled-job state | When it is kept in files; when the site keeps a database it is in the database copy |
| Add-on files | Forms and their submissions, calendars, feed records |
| Search index | Rebuilt automatically if missing |
/%

### What is NOT included

%%table-striped
|| Data || How to back up ||
| The backup key | Save it off the server (see What to keep safe below) |
| TLS certificate files | Reissue them on a new server |
| Shares and notifications | Copy `$FAST_STORAGE/` |
| Sign-in sessions | Not needed: users sign in again |
| Media files (photos/videos) | Back up media source folders at the OS/NAS level |
/%

> __Important:__ The backup alone is __not a complete backup__. [Admin → Backup Management|/admin/backup] can restore the whole site from it, except pages, user accounts and settings.
> To restore those, put back a copy of the data folders taken while the server was stopped.

### What to keep safe

- __Administrators: the backup key.__ Every site makes a backup key the first time it starts, and every backup is encrypted with it. It is the one thing a restore on a new server needs: with it, everything in a backup comes back, including every administrator's passkeys. [Admin → Backup Management|/admin/backup] shows the key's fingerprint and a banner on the admin dashboard asks you to save the key until an administrator confirms it is saved. __Show the key to copy it__ (after signing in again), keep it in a password manager or on paper away from this server, then press __I have saved this key off the server__. On a new server, put the saved key in the instance `.env` as `NGDPBASE_BACKUP_KEY` before it first starts.
- __Administrators: a copy of the site's `.env`, if you want one.__ __Download .env__, beside the backup key on [Admin → Backup Management|/admin/backup], downloads the site's `.env` file exactly as it is, the backup key included, after signing in again. This file holds every secret of the site in plain text — keep it somewhere as safe as a password manager, never in an ordinary folder or an email. Each download is recorded with who took it. When a key is added to the `.env` file or removed from it — one the site makes for itself, or one someone typed in — the admin dashboard lists Backup under "Working, but needs your attention" and administrators get one notification naming the keys that changed (their names only, never their contents). Download the file again, keep the new copy, then press __I have saved .env off the server__. Because the file holds the backup key, that one press also counts as saving the backup key. A site that already has a `.env` when it moves to this version is not asked: the keys it has then are taken as saved, and only later changes ask.
- __Administrators: the shared folders' recovery words.__ Each shared folder's key is kept under the site's shared-folders key (`NGDPBASE_SHARED_FOLDERS_KEY`, made when the site first starts and kept in `.env`) and under the organization's twelve recovery words. [Admin → Backup Management|/admin/backup] shows the shared-folders key's fingerprint, and asks for a saved copy of `.env` until an administrator confirms one: the same __I have saved .env off the server__ counts for it. The recovery words are made there too, with __Make the recovery words__, and shown once to the administrator who makes them, with __Download as a file__ and __Print__; that administrator types all twelve back and ticks that they saved them before anything is kept. No shared folder can be made until they confirm, and until then administrators see a reminder; if they cannot confirm, any administrator can discard the words and make a new set. __Make a new set of recovery words__ replaces words that were lost: it asks you to sign in again, and when the new words are typed back the old ones stop working. See [Shared Folders Recovery Words].
- __Everyone with an encrypted vault: your recovery words.__ The files in an encrypted vault are locked with your own key. If you forget your password, your 12 recovery words are the only way back in: nobody else, not even an administrator or a backup, can open those files without them. You confirm you saved them when they are shown to you; until you have, a reminder on the home page, your profile and your vaults' pages names the vaults they protect. See [Your Recovery Words].

### Encryption

- __With the backup key set__ (`NGDPBASE_BACKUP_KEY`, in the environment or the instance `.env`), every file of a backup is encrypted with it: the backup document, every `.tar.enc` beside it and the databases. Without the key none of it can be read, and a restore under a different key is refused with a plain message. Keep a copy of the key somewhere other than this server.
- __Without the backup key__, the backup is __not encrypted__: the document holds hashed passwords and settings with their secrets, and the files beside it hold attachments and records as they are. The sign-in credentials and the databases are left out. While the key is missing the admin dashboard lists Backup under "Working, but needs your attention", and admins get one notification about it, the first time only, naming what is left out; a backup sends no notification of its own about it. A backup that misses something for any other reason still notifies admins every time. Keep such backups as safe as the data folders.

### When backups stop working

Backups never fail silently. The admin dashboard lists Backup as __not working__, and administrators get one notification, "Backups are not working", when:

- __A backup fails.__ The backup folder is out of space or can't be written to, the encryption fails, part of the site could not be backed up ("A backup is incomplete"), or the finished backup does not read back. The dashboard gives the reason and the date of the last good backup. It stays there, even after a restart, until a backup succeeds.
- __No good backup is recent enough.__ The dashboard says "No good backup since" and the date, or "never" on a site that has not made one yet — a new site shows this until its first backup. With Auto Backup on, "recent enough" is twice the longest gap between scheduled backups (two days for a daily backup); with it off, 7 days. The site checks this when it starts and every hour.

Before it writes anything, a backup checks that the backup folder has room for it (at least one and a half times the size of the last backup) and stops with a plain reason instead of writing half a file. After writing, it reads the backup back — decrypts, unpacks and checks it. A backup that does not read back is removed and counts as a failure.

[Admin → Backup Management|/admin/backup] and the admin dashboard show the last successful backup (when, in your own time zone, its size and the folder it is in), when the next automatic backup is due, and how much free space the backup folder has.

### What a restore does not bring back

__Restore the whole site__ on [Admin → Backup Management|/admin/backup] puts back the databases, attachments, role membership, user and contact records, organizations, footnotes and comments, sign-in credentials, the audit log, scheduled-job state, add-on files and the site's keys and secrets, all together, at the next restart. __Restore the databases only__ puts back only the databases and what is kept in them. The screen lists what is and is not put back before you confirm. Either way, these stay as they were on the site before the restore, or are in no backup at all:

- Shares (share links stay as they are) and notifications
- Sign-in sessions
- The backup key and the database key (the site keeps its own)
- TLS certificate files
- The media index
- Pages, user accounts and settings: a restore does not put them back yet
- Anything the backup left out, such as the sign-in credentials of a backup taken without the backup key

Scheduled jobs that ran between the backup and the restore are no longer in the job history after it. They are __never run again__ by a restore: a job that was running when the backup was taken is marked as cut off by the restore, and the schedule goes on from the next time after the restart.

After a restore is put in place, admins get a __critical notification__ that lists everything above that applies, and each job that ran between the backup and the restore with its last run time and result, so you can decide whether any of them needs running again.

### Databases

When the site keeps a database (`ngdpbase.database.provider` is `sqlite`), every backup also copies it, together with the database of every add-on that declares one, including add-ons that are turned off.

- __Encrypted, always.__ The copies are encrypted with the backup key, `NGDPBASE_BACKUP_KEY`, set in the environment or the instance `.env`. It is its own secret: use a different value from `NGDPBASE_DATABASE_KEY`. Keep a copy of it somewhere other than the backups; without it, a backup's databases cannot be restored.
- __No key, no database backup.__ Without `NGDPBASE_BACKUP_KEY` nothing unencrypted is written in its place. The admin dashboard reports the database as not working from the start, and every backup sends admins a notification that it is incomplete.
- __Taken while the site runs.__ Every database is copied at the same moment, without stopping the site or slowing its pages.
- __Files beside the backup.__ Each database is its own file in the backup directory, named after the backup with `.application.db` or `.addon-<name>.db` added. They are kept and removed together with their backup, and each backup's __Download__ on [Admin → Backup Management|/admin/backup] is one `.tar` holding all of them. The backup key is never in the download: keep it somewhere other than this server.
- __Same key twice.__ If `NGDPBASE_BACKUP_KEY` is the same as `NGDPBASE_DATABASE_KEY`, backups still run, but the dashboard and a notification warn you, as for a missing key. Each backup remembers a short fingerprint of its key (never the key itself), so restoring with a different key is refused with a plain message.
- `ngdpbase.database.backup.worker-timeout-ms` is how long the copy may take before it is stopped and reported as failed (default one hour).

A database restore is __staged__: the site first takes a fresh backup of its current data, then prepares the backup's databases beside the live ones. Nothing changes until the next restart, when the prepared files are put in place before any database opens. The previous files are kept beside them, named `*.pre-restore`. If any database could not be prepared, none is used and admins are told. See [Restore Process](#restore-process) below.

## 2. Filesystem Backup

Back up the following directories using your OS, NAS, or cloud backup tool:

%%table-striped
|| Directory || Contains ||
| `$SLOW_STORAGE/pages/` | All page markdown files + version history |
| `$SLOW_STORAGE/attachments/` | All uploaded attachment binary files |
| `$FAST_STORAGE/` | Users, sessions, config overrides, logs, search index |
/%

`FAST_STORAGE` and `SLOW_STORAGE` are set in your instance `.env` file.

## 3. Media Backup

Media files are __read-only__ to ngdpbase — it indexes them but does not own them.
Back up media at the storage level (NAS, external drive, cloud).

The media index (`media-index.json`) is regenerated automatically on the next scan via
[Admin → Media → Rescan|/admin/media]. It does not need to be backed up explicitly.

## Auto Backup

When __Auto Backup__ is enabled, the server automatically runs the structured backup at the
configured time and day(s). Configure it at [Admin → Backup Management|/admin/backup].

> Auto backup makes the same backup as the manual button.
> It does __not__ back up what is listed under "What is NOT included", or media.

## Recommended Backup Process

### Step 1 — Structured backup (weekly or more often)

1. Go to [Admin → Backup Management|/admin/backup]
2. Click __Create & Download Backup__
3. Store the downloaded `.tar` file in a safe location (cloud storage, external drive), and the backup key somewhere else

Or enable __Auto Backup__ to have this run automatically on a schedule.

### Step 2 — Filesystem backup (daily recommended)

Use your OS, NAS, or cloud backup tool to snapshot:

- `$SLOW_STORAGE/pages/`
- `$SLOW_STORAGE/attachments/`
- `$FAST_STORAGE/` (or at minimum the `users/` and `config/` subdirectories)

### Step 3 — Media backup (as needed)

Back up your configured media folders independently.

## Restore Process

### Restore the whole site

Every site has a __Restore the whole site__ section on [Admin → Backup Management|/admin/backup]:

- 1 Choose a backup stored on the server. The list shows each backup's date, and marks one taken without the backup key; there is no upload.
- 2 Type the site name to confirm, then press __Restore the whole site__.
- 3 The site takes a fresh backup of its current data, then prepares everything the chosen backup can put back, beside the current data. You get a notification when it is ready, or why it could not be prepared. The page names that fresh backup (the safety backup); it is in the list of stored backups, and restoring it undoes this restore.
- 4 Restart the site. Everything prepared is put in place together as it starts, or nothing is. The site never restarts on its own.

The section lists what it puts back and what it does not before you confirm. The site's keys and secrets (its `.env` file) come back only from an encrypted backup, and an encrypted backup can be restored only on a server that has the same backup key. While a restore waits for the restart, the page shows which backup it is, when it was prepared and by whom, with __Cancel staged restore__ and __Replace it__ (the same typed confirmation).

### Restore the databases only

When the site keeps databases, a second section, __Restore the databases only__, does the same for the databases alone:

- 1 Choose a backup stored on the server that holds databases.
- 2 Type the site name to confirm, then press __Restore__.
- 3 The site takes a fresh backup of its current data, then prepares the chosen backup's databases, and tells you when they are ready.
- 4 Restart the site. The prepared databases are put in place as it starts.

__Restores the databases only. Pages, users and settings are not changed.__ It is not offered while a whole-site restore waits for the restart, since that includes the databases. Restoring needs the backup key the backup was made with.

### Restore page and attachment files

1. Stop the server: `./server.sh stop`
2. Copy backed-up `pages/` and `attachments/` directories back to their original locations
3. Restart the server: `./server.sh start`

### Restore after complete loss (new machine)

1. Install ngdpbase and configure `.env` with the same `FAST_STORAGE` and `SLOW_STORAGE` paths
2. Copy `pages/` and `attachments/` from backup to `$SLOW_STORAGE/`
3. Copy `users/` and `config/` from backup to `$FAST_STORAGE/`
4. Put the saved backup key in the instance `.env`, start the server, put the backup's `.tar` contents in the backup directory, and use __Restore the whole site__
5. Trigger a media rescan if applicable
