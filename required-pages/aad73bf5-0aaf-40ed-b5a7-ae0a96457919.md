# Backup

[{$pagename}] operations allow administrators to protect platform data against loss.

ngdpbase has __two separate layers of data__ that require different backup strategies.
A complete backup requires both.

## 1. Structured Data Backup ("Backup Data" button)

Found at [Admin → Backup Management|/admin/backup].

The __Create & Download Backup__ button:

1. Calls `backup()` on every registered manager
2. Aggregates results into a single JSON document
3. Compresses with gzip
4. Downloads it as one `.tar` file: the backup document (`<timestamp>-ngdpbase-backup.json.gz`) and, when the site keeps databases, an encrypted copy of each
5. Retains the last [{ConfigAccessorPlugin key="ngdpbase.backup.max-backups" valueonly=true}] backups on the server

### What IS included

%%table-striped
|| Data || Notes ||
| Configuration settings | All `ngdpbase.*` config keys |
| User accounts and roles | Usernames, hashed passwords, role assignments |
| Access control lists | Page-level permissions |
| Attachment metadata | Filenames, hashes, MIME types, page links |
| Search index | Rebuilt automatically if missing |
| Page files (`.md`) | Every page, including required pages |
| Page version history | Every saved version of every page |
/%

### What is NOT included

%%table-striped
|| Data || How to back up ||
| Attachment binary files | Copy `$SLOW_STORAGE/attachments/` |
| Page version history of private stores | Copy `$SLOW_STORAGE/pages/vaults/` |
| Media files (photos/videos) | Back up media source folders at the OS/NAS level |
/%

> __Important:__ The Backup Data button alone is __not a complete backup__.
> Without a filesystem copy of your attachments, you cannot fully restore the platform.

### Databases

When the site keeps a database (`ngdpbase.database.provider` is `sqlite`), every backup also copies it, together with the database of every add-on that declares one, including add-ons that are turned off.

- __Encrypted, always.__ The copies are encrypted with the backup key, `NGDPBASE_BACKUP_KEY`, set in the environment or the instance `.env`. It is its own secret: use a different value from `NGDPBASE_DATABASE_KEY`. Keep a copy of it somewhere other than the backups; without it, a backup's databases cannot be restored.
- __No key, no database backup.__ Without `NGDPBASE_BACKUP_KEY` nothing unencrypted is written in its place. The admin dashboard reports the database as not working from the start, and every backup sends admins a notification that it is incomplete.
- __Taken while the site runs.__ Every database is copied at the same moment, without stopping the site or slowing its pages.
- __Files beside the backup.__ Each database is its own file in the backup directory, named after the backup with `.application.db` or `.addon-<name>.db` added. They are kept and removed together with their backup, and each backup's __Download__ on [Admin → Backup Management|/admin/backup] is one `.tar` holding all of them. The backup key is never in the download: keep it somewhere other than this server.
- __Same key twice.__ If `NGDPBASE_BACKUP_KEY` is the same as `NGDPBASE_DATABASE_KEY`, backups still run, but the dashboard and a notification warn you, as for a missing key. Each backup remembers a short fingerprint of its key (never the key itself), so restoring with a different key is refused with a plain message.
- `ngdpbase.database.backup.worker-timeout-ms` is how long the copy may take before it is stopped and reported as failed (default one hour).

A database restore is __staged__: the site first takes a fresh backup of its current data, then prepares the backup's databases beside the live ones. Nothing changes until the next restart, when the prepared files are put in place before any database opens. The previous files are kept beside them, named `*.pre-restore`. If any database could not be prepared, none is used and admins are told. See [Restore Process](#restore-process) below.

## 2. Filesystem Backup

Back up the following directories using your OS, NAS, or cloud backup tool:

%%table-striped
|| Directory || Contains ||
| `$SLOW_STORAGE/pages/` | All page markdown files + version history |
| `$SLOW_STORAGE/attachments/` | All uploaded attachment binary files |
| `$FAST_STORAGE/` | Users, sessions, config overrides, logs, search index |
/%

`FAST_STORAGE` and `SLOW_STORAGE` are set in your instance `.env` file.

## 3. Media Backup

Media files are __read-only__ to ngdpbase — it indexes them but does not own them.
Back up media at the storage level (NAS, external drive, cloud).

The media index (`media-index.json`) is regenerated automatically on the next scan via
[Admin → Media → Rescan|/admin/media]. It does not need to be backed up explicitly.

## Auto Backup

When __Auto Backup__ is enabled, the server automatically runs the structured backup at the
configured time and day(s). Configure it at [Admin → Backup Management|/admin/backup].

> Auto backup covers only structured data (same as the manual button).
> It does __not__ back up page files, attachments, or media.

[{$pagename}] [Configuration System] has the following values:
[{ConfigAccessorPlugin key="ngdpbase.backup*"}]

## Recommended Backup Process

### Step 1 — Structured backup (weekly or more often)

1. Go to [Admin → Backup Management|/admin/backup]
2. Click __Create & Download Backup__
3. Store the `.json.gz` file in a safe location (cloud storage, external drive)

Or enable __Auto Backup__ to have this run automatically on a schedule.

### Step 2 — Filesystem backup (daily recommended)

Use your OS, NAS, or cloud backup tool to snapshot:

- `$SLOW_STORAGE/pages/`
- `$SLOW_STORAGE/attachments/`
- `$FAST_STORAGE/` (or at minimum the `users/` and `config/` subdirectories)

### Step 3 — Media backup (as needed)

Back up your configured media folders independently.

## Restore Process

### Restore the databases

When the site keeps databases, [Admin → Backup Management|/admin/backup] has a __Restore Databases__ section:

1. Choose a backup stored on the server. The list shows each backup's date and the databases it holds; there is no upload.
2. Type the site name to confirm, then press __Restore__.
3. The site takes a fresh backup of its current data, then prepares the chosen backup's databases. You get a notification when they are ready, or why they could not be prepared.
4. Restart the site. The prepared databases are put in place as it starts. The site never restarts on its own.

Only the databases are restored; settings, users and pages are not changed by this. While a restore waits for the restart, the page shows which backup it is, when it was prepared and by whom, with __Cancel staged restore__ and __Replace it__ (the same typed confirmation). Restoring needs the backup key the backup was made with.

There is no screen to restore the rest of a backup document (settings, users) yet.

### Restore page and attachment files

1. Stop the server: `./server.sh stop`
2. Copy backed-up `pages/` and `attachments/` directories back to their original locations
3. Restart the server: `./server.sh start`

### Restore after complete loss (new machine)

1. Install ngdpbase and configure `.env` with the same `FAST_STORAGE` and `SLOW_STORAGE` paths
2. Copy `pages/` and `attachments/` from backup to `$SLOW_STORAGE/`
3. Copy `users/` and `config/` from backup to `$FAST_STORAGE/`
4. Start the server, put the backup's `.tar` contents in the backup directory, and use __Restore Databases__ for the databases
5. Trigger a media rescan if applicable
